3三個必須先解的結構關卡

關卡 1 · runtime.js 是生成的，不能直接改

scripts/generate-yuanzhan-v5.mjs 從 owner 的原型 HTML 產生 runtime，並把來源 SHA256 寫進檔頭。

  • 行為修正只能走 source-patches.mjs —— 窄字串替換，比對不到就 throw（刻意的：來源變了要人看過）
  • 新功能走附加的 *.source.js，在 init 前插入（已有 5 個：extensions / replies / journal-cockpit / timeline-participants / template-objects）
  • 既有覆寫慣例：const orig = VIEWS.project; VIEWS.project = tab => ...（專案這一項已被包了 4 層）

結論：新模組是第 6 個擴充檔 operating-canvas.source.js，不動原型、不改 SHA。不要去改 reference HTML 重新 baseline —— 那會讓所有既有 patch 一次失效。

關卡 2 · fidelity gate 綁著舊的模組清單

scripts/verify-yuanzhan-v5.cjs 讀 reference/workspaces.json，逐一走訪 8 個模組 30 個分頁並逐頁截圖比對，斷言 shell 尺寸、無 inline handler、無 NaN。

  • 合併模組 → navigate() 找不到「時間線」的 rail 項目 → 直接紅
  • 基準截圖裡有 timeline-0..3.png、desk-0..2.png、project-0..4.png

結論：fidelity 套件分叉：保留 verify-yuanzhan-v5 驗「舊版仍可用」（flag 關閉時），新增 verify-operating-canvas 驗新模組並建立自己的基準。等舊模組正式下架，才更新 workspaces.json 並封存舊基準。

關卡 3 · 兩個資料面互不相通

v5 是記憶體 store（showcase／empty，ARC-040 契約）；Prisma 那側有 Project／Task／PhaseNode／Milestone，但沒有 events、rhythm、occasion。

  • v5 的「專案」沒有里程碑，只有 delivery[] 字串陣列
  • Prisma 的 ProjectMilestone 掛在 ProjectPhaseNode 之下，和 PLN-072 假設的「Milestone → Project」差一層

結論：UI 層先走（記憶體 store 加三軌，不碰 schema），DB 層後走。DB 層要先決定 ProjectPhaseNode 是保留成「階段」（和里程碑並存）還是廢掉；我的建議是保留，讓 Phase（一段時間）與 Milestone（一個時間點）各司其職，PLN-072 的 schema 相應修正為 Project → Phase → Milestone → Objective → Task。

回滾的三個層級

  • 畫面層（秒級）：設定切 legacy，舊模組回到 WB[]，新模組隱藏。資料不動 —— 因為兩邊讀同一個 spine()。
  • 資料層（T2 之前可逆）：遷移腳本產生的三軌資料與原 DB.events 並存不刪，直到 T4 確認後才移除舊陣列。舊模組在 legacy 模式下仍讀得到原本的 events。
  • 程式層：新模組全在一個擴充檔裡，git revert 一個檔案就回到 T1 狀態，不影響其他 5 個擴充檔。
