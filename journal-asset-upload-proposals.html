日誌檔案物件：上傳 → Cloudflare R2 → 可 @ 引用

把圖片、文件（docx / xlsx / pptx / pdf）、音訊、影片從電腦或手機丟進日誌，bytes 直接進 Cloudflare R2， 而檔案本身變成一個物件 —— 有參考碼、進得了物件索引、在任何一行打 @ 就引用得到。

Proposal · 2026-09-28 · 尚未實作 含 5 項須 Owner 決定

一、這件事有一半已經做完了先盤點，才知道真正缺什麼

這不是從零開始的功能。R2 的管線在 PLN-064 已經走到 Stage 4A， 日誌的物件機制在 YZUI-012 已經有物件索引。缺的是把兩者接起來。

檔案可以被 @沒有 mentionHits() 只列 issue／project／txn／decision／event／doc_object。檔案不是物件。

二、真正的三個缺口不是「還沒做上傳」那麼簡單

缺口 1

檔案不是物件，所以 @ 不到

系統裡「可以被 @」的定義很明確：出現在 mentionHits() 裡、有 ty 與 rid、 能被 replaceWithObj() 嵌成區塊、objHtml() 畫得出卡片、objJump() 打得開。 檔案五樣都沒有。

解法　新增物件型別 asset，把這五個接點各補一條分支。

缺口 2

白名單與 5 MB 上限是為「文字檔＋憑證照片」設計的

現在的限制不是隨便訂的 —— 它配合的是文件庫那批 md／csv／發票照。 一份 pptx 動輒 20 MB，一段會議錄音 80 MB，一支手機影片 300 MB。 這不是把數字調大就好：大檔需要續傳，5 MB 檔不需要。

解法　白名單依 kind 分級，各自一個上限；超過門檻改走 multipart。

缺口 3

日誌沒有入口，而手機根本沒有入口

上傳目前只存在於「文件」抽屜的按鈕。日誌是每天寫東西的地方，卻連貼上截圖都不行。 手機上更麻煩：# 選單要打字才叫得出來，而拖放不存在。

解法　四道門收斂成一個 assetIntake()；手機那道門是系統原生的拍照／相簿／檔案。

四、流程設計：四道門，一條管線入口分歧，之後完全收斂

為什麼是這四道門

門裝置理由與代價
拖放到某一行桌機 放在哪一行，檔案就誕生在哪一行 —— 與 # 召喚的「物件誕生在這一行」同一個心智模型。 需要在 .eb 上加 drop，但那裡已經有 dragover／drop 處理區塊拖曳， 必須先判斷 dataTransfer.files.length 才不會打架。
貼上 ⌘V桌機 截圖是最高頻的一種「檔案」。runtime.js:7900 已有 paste 監聽（只取純文字）， 加一條 clipboardData.files 分支即可。截圖沒有檔名，需自動命名 截圖 09-28 14:32.png。
# 召喚 → 附件兩者皆可 不發明新語法。使用者已經知道「# 生出東西」，附件也是生出一個物件。 在 SUMMON 的「物件」組加一項，applySummon 走檔案選擇器而非 openForm。
行首 ＋ → 三選一手機為主 手機沒有拖放、⌘V 不好按、# 要切輸入法。原生解法是三個 <input type="file">： accept="image/*" capture="environment"（拍照）、accept="image/*,video/*"（相簿）、 不限（檔案）。iOS／Android 會自己叫出正確的系統選單。

五、大檔：multipart 的真正理由不是 5 GiB 上限，是續傳

R2 單次 PUT 可以吃到 5 GiB，所以就算一支 500 MB 的影片，技術上也能一次 PUT 完。 問題在於：單次 PUT 沒有中繼點。手機在電梯裡掉訊號，480 MB 全部重來。

因此門檻不該訂在 R2 的能力上限，而訂在「重傳一次會不會讓人想砸手機」。建議 64 MB：

檔案大小路徑行為
≤ 64 MB單次預簽 PUT現有 putToR2() 不用改。失敗就整份重來，代價可接受。
> 64 MBmultipart（8 MB／段） 伺服器 CreateMultipartUpload → 逐段預簽 UploadPart（PUT）給瀏覽器 → 瀏覽器並行 3 段 → 伺服器 CompleteMultipartUpload。斷線只重傳未完成的段。

R2 的預簽只支援 GET／HEAD／PUT／DELETE，不支援 HTML form 的 POST。 而 CreateMultipartUpload 與 CompleteMultipartUpload 在 S3 API 裡正是 POST —— 所以這兩步必須留在伺服器用憑證直接呼叫，只有中間的 UploadPart 能預簽下放。 這剛好也是比較安全的切法：瀏覽器永遠拿不到能開新 upload 的權限。

上限：每個 multipart 最多 10,000 段；8 MB × 10,000 = 80 GB，遠超任何實際需求。 段大小除最後一段外必須一致。

六、卡片長什麼樣五種 kind，同一個骨架

沿用 objHtml() 既有的 .eb-obj 骨架（chip + 標題 + 參考碼 + 一列 .pf 欄位）， 只在骨架下方依 kind 換掉「主體」那一塊。這樣卡片在日誌、在文件物件段落、在物件索引時間軸都長一樣。

七、預覽做到哪裡分級，不要什麼都做

docx / xlsx / pptx 瀏覽器不能原生開，這是整個提案裡技術選擇最關鍵的一格。三條路：

  • (a) 只給圖示與下載 —— 零成本，但使用者得離開頁面才看得到內容。
  • (b) 伺服器轉 PDF（LibreOffice headless）—— 預覽最完整，但 Vercel serverless 跑不動， 要另起 container 或 worker。基礎設施成本最高，且會成為新的維運面。
  • (c) 前端函式庫解析（mammoth.js / SheetJS / JSZip）—— 不需要任何新基礎設施， 而且順便拿到文字，可以餵進物件索引的搜尋。

建議：P1 走 (a) 先上線，P3 走 (c)。(b) 除非 Owner 要求像素級還原，否則不做。

影音的 TTL 坑

現行下載預簽 TTL 是 5 分鐘。對圖片與 PDF 沒問題 —— 載入就結束了。 對影音會壞：<video> 是靠 HTTP Range 一段段續讀的，使用者看到第 8 分鐘時再拉一次資料， 那張網址早就過期，直接 403，播放器只會顯示「無法播放」而不告訴你原因。

八、資料模型沿用 SCH-005 的欄位、RES-018 的參考碼

新增一張表。欄位刻意與 SCH-005 的 FileAsset／MediaAsset 對齊， 未來若要合併不必改欄位名。

/// 日誌／文件庫／金流共用的一份檔案資產。origin 記住它是從哪道門進來的。
model OperatingAsset {
  id            String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  workspaceId   String   @map("workspace_id") @db.Uuid
  refCode       String   @unique @map("ref_code")   // AST-JRNL-000124-20260928 · 指派一次，永不重生成
  kind          String                                  // image | doc | sheet | slide | pdf | audio | video | other
  displayName   String   @map("display_name")           // 可改；改了不影響 refCode
  objectKey     String   @map("object_key")            // operating/{workspaceId}/asset/{yyyy-mm}/{uuid}{ext}
  bucket        String
  mimeType      String?  @map("mime_type")
  sizeBytes     Int?     @map("size_bytes")
  contentHash   String?  @map("content_hash")           // finalize 時由 HeadObject 的 ETag 寫入
  status        String   @default("uploading")          // uploading | ready | failed
  uploadId      String?  @map("upload_id")              // multipart 進行中才有；complete 後清空
  /// team = 全員可見；personal = 只有作者讀得到（下載授權依這欄）
  space         String   @default("team")
  authorKey     String?  @map("author_key")
  origin        String   @default("journal")            // journal | library | cashflow
  /// 誕生在哪一天的日誌 —— 物件索引的「來源」欄靠它，日誌那行刪了也還在
  bornDay       DateTime? @map("born_day") @db.Date
  bornAt        DateTime? @map("born_at")
  /// 抽出來的純文字，讓物件索引搜得到內容（P3）
  extractedText String?  @map("extracted_text")
  /// 音訊／影片的時長與轉錄（P2／P4）
  durationSec   Int?     @map("duration_sec")
  transcript    String?
  deletedAt     DateTime? @map("deleted_at")
  createdAt     DateTime @default(now()) @map("created_at")
  updatedAt     DateTime @updatedAt @map("updated_at")

  @@index([workspaceId, status], map: "operating_assets_workspace_status_idx")
  @@index([workspaceId, bornDay], map: "operating_assets_workspace_day_idx")
  @@unique([bucket, objectKey], map: "operating_assets_object_key_unique")
  @@map("operating_assets")
}

十、須 Owner 決定的五件事沒定案之前不寫對應的程式碼

D1各 kind 的單檔上限

現況全部 5 MB。影片一定要放寬，但放多寬牽涉 R2 帳單與手機上傳體感。

  • 保守　圖片 25 MB · 文件 50 MB · 音訊 200 MB · 影片 500 MB
  • 寬鬆　圖片 50 MB · 文件 100 MB · 音訊 500 MB · 影片 2 GB

建議保守　兩人內部使用，500 MB 已能裝 20 分鐘 1080p。放寬隨時可以，收緊會讓既有檔案變成違規資料。

D2檔案只有一個家，還是兩個

現在文件庫用 OperatingLibraryFile，金流憑證在 cashflow-faces.source.js 自己上傳。 日誌附件如果再開一張表，同一份檔在系統裡就有三個家 —— 搜尋要搜三次，引用要認三種 id。

  • 合併　OperatingAsset 一張表，origin 分流；文件庫與金流憑證都改成它的檢視。 日誌上傳的檔案自動出現在文件庫。
  • 並存　日誌附件自成一張表，文件庫維持現狀，之後再說。

建議合併，但分兩步　P0 先只建 OperatingAsset 給日誌用， P4 再把文件庫與金流的讀寫切過來。並存會讓「@ 得到日誌的檔、@ 不到文件庫的檔」變成長期的怪異行為。 這是本提案最大的架構變更，需要明確點頭。

D3影音播放的網址策略

5 分鐘 TTL 會讓影片播到一半 403。

  • A 延長 TTL　影音專用 1–6 小時（R2 上限 7 天）。最簡單。代價：網址若外流，該時段內任何人可看。
  • B 播放器自動換網址　偵測 403／error 事件重簽，記住 currentTime 後接回去。 TTL 可維持 5 分鐘，但跨瀏覽器行為不一，seek 時容易卡頓。
  • C 自家 Range proxy　/api/.../stream?assetId= 由伺服器代讀。授權最乾淨， 但 bytes 改走 Vercel —— R2「出口免費」的好處被吃掉一半，且長影片會壓到 serverless 執行時間上限。

建議 A，TTL 設 1 小時　bucket 是 private、網址只發給登入過且有席位的人、內容是內部素材。 真的有外部分享需求時再上 C。

D4Office 預覽做到哪一級

  • 只下載　零成本。
  • 前端解析（建議）　mammoth／SheetJS／JSZip，順便拿到文字餵搜尋。約 +300 KB 前端體積，可延遲載入。
  • 伺服器轉 PDF　還原度最高，但要新的 container 基礎設施與維運面。

建議前端解析，排在 P3　P1 先只給下載，不擋上線。

D5刪除語意

現行規則是「日誌刪掉那一行，物件不受影響」（runtime.js:4253 的提示文字就這麼寫）。 但檔案多了一個問題：物件本身被刪的時候，R2 的 bytes 要不要一起刪？

  • 軟刪　只寫 deletedAt，bytes 永久留在 R2。誤刪救得回來，但儲存費用只增不減。
  • 軟刪 ＋ 30 天後硬刪　有反悔期，費用可控。需要一支排程。

建議軟刪 ＋ 30 天　排程可以延到 P4 再寫，欄位現在先留好。

十一、權限與安全其中一條是既有的洞

議題現況提案
bucket 公開性已正確 維持 private ＋ 伺服器簽網址。RES-022 §3：R2 public bucket 是全有全無， 無法表達「私人檔 vs 客戶可見」。
下載授權有洞 現行 GET 只檢查 key 開頭是 operating/。 任何有席位的人拿到 key 就能換下載網址，包含別人 space:'personal' 的私人文件。 提案：先查 DB 這個 asset 的 workspaceId 與 space／authorKey， 通過才簽。
object key 形狀半套 現在是 operating/{yyyy-mm}/{uuid}{ext}，沒有租戶維度。 改為 operating/{workspaceId}/asset/{yyyy-mm}/{uuid}{ext}， 讓「這個 key 屬於哪個工作區」從 key 本身就看得出來（ARC-033 租戶隔離不變量）。
可執行內容部分 副檔名白名單已擋掉 exe／sh。新增時必須明確拒絕巨集格式 .docm／.xlsm／.pptm，以及 .svg（可內嵌 script）。
副檔名偽造沒做 前端送什麼名字伺服器就信什麼。finalize 時用 HeadObject 拿真實 ContentType 對照； 嚴格版需讀 magic bytes，排 P3。
掃毒欄位存在 scanStatus 在 SCH-005 已有，但永遠 NOT_REQUIRED。 兩人內部使用暫不接掃毒服務 —— 但要在文件寫明這是已知且接受的風險， 而不是假裝這件事不存在。開放給客戶（R2STORE-007）之前必須補。
bytes 不進寫入佇列必須守住 ARC-042 的 diff 佇列送的是 1–3 列差異。 prototype 模式現在把檔案存成 base64 data URL（extensions.source.js:167）—— 一旦那條路徑接上持久化，一張 5 MB 的圖會變成約 7 MB 的 JSON 進佇列。 asset 只送 metadata，data URL 僅限 prototype 模式且不得持久化。

十三、驗收條件P0 + P1 合計 14 條

  1. 拖放一張圖到某一行 → 該行下方出現 uploading 卡片，不是整頁刷新。
  2. ⌘V 貼上截圖 → 自動命名 截圖 MM-DD HH:mm.png 並上傳。
  3. # 選單打「附件」找得到，選了會開系統檔案選擇器。
  4. 手機 390px 寬：行首 ＋ 叫得出拍照／相簿／檔案三選一，版面不爆。
  5. 拖放檔案時不會誤觸既有的「拖曳區塊排序」。
  6. 上傳中關掉分頁再回來 → 該列仍是 uploading，卡片顯示「已中斷 · 重試」。
  7. finalize 時伺服器 HeadObject 大小對不上 → 狀態 failed，不會變 ready。
  8. 只有 ready 的 asset 會出現在 @ 選單。
  9. 隔一天在另一行 @ 同一個檔 → 引用同一個 id，R2 不產生第二份 bytes。
  10. 刪掉日誌那一行 → 檔案仍在物件索引，來源欄標「來源日誌那一行已刪除」。
  11. 物件索引的型別 facet 出現「圖片／文件／音訊／影片」，數量正確、0 筆淡化不隱藏。
  12. 用另一個席位的帳號拿別人 personal 檔的 key 打 GET → 403，而不是拿到下載網址。
  13. 上傳 .docm → 被拒，錯誤訊息說得出原因。
  14. white／orange／black／brand 四主題下卡片、進度條、播放器皆可讀，無硬編碼 hex。

十四、被否決的替代方案寫下來，免得三個月後又被提一次

bytes 經自家伺服器中轉上傳　—— Vercel 的 request body 上限約 4.5 MB，一支影片直接爆； 而且會把 R2 出口免費的優勢丟掉。既有的預簽直傳已經是對的做法。
檔案存成 base64 data URL 放進日誌區塊　—— prototype 模式現在就是這樣。 一旦接上持久化，5 MB 的圖變成約 7 MB 的 JSON 進 ARC-042 的 diff 佇列。 這正是 uploads 路由註解裡寫的那個理由。
用 public bucket 省掉簽網址　—— RES-022 §3：R2 public bucket 全有全無， 沒有 per-object 隱私。私人文件與客戶交付物混在同一桶。
伺服器端 LibreOffice 轉 PDF 做 Office 預覽　—— Vercel serverless 跑不動， 要新起 container。為了預覽而開一條新的維運面，代價不成比例。
讓檔案只當「附件」，不做成物件　—— 那就 @ 不到，等於沒有解到題。 附件是黏在某一行的裝飾，物件才有唯一的家、參考碼與反向引用。
用 # 引用既有檔案　—— 違反既有語意：# 生新物件、@ 引既有物件。 檔案兩邊都要用：# 附件＝上傳新檔（生新物件），@ 檔名＝引用既有檔。
為日誌附件另寫一套上傳路由　—— PLN-064 Stage 4 已明文要求重用 Stage 2 的路由， 而非平行實作。
一次做完 P0–P4　—— 影音、multipart、Office 解析三件事各自有獨立的失敗模式。 綁在一起發，任何一個壞掉整包都上不了。

十五、風險與停止條件

  • R2 帳單　R2 出口（egress）免費，這是當初選它的主要理由；但儲存與 Class A 操作要錢。 影片一進來，用量級距會跳一階。建議 P2 上線後看一個月實際帳單再決定要不要收緊 D1。
  • 孤兒物件　presign 發出去但使用者關掉分頁，R2 可能已有 bytes 而 DB 是 uploading。 排程清理（uploading > 24h）必須和 P0 一起做，不能延後 —— 延後就會累積成一筆查不清的儲存費。
  • 同一 key 併發寫入　R2 對同一 key 的寫入限制是每秒 1 次；因為 key 帶 uuid，正常不會踩到， 但「重試」若沿用同一個 key 就可能。所以重試換新 key。
  • UI-088 Revision Mode　日誌屬 UI-088，狀態 COMPLETED。 新增上傳入口是行為變更，依 REF-003:202 需 Product Owner 點頭，且不得新增假 UI ID。
  • 停止條件　若實作中發現需要改 ARC-042 寫入佇列的形狀（例如 assets 不能走同一條 diff）， 或需要新增任何批次寫入／刪除動作（ARC-030 §8 在稽核機制到位前一律拒絕），停下回報。
