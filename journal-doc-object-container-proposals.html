元件容器（Standup／1:1／會議記錄／回顧／研究筆記）還是崩潰 — 根因與三個修復方向

上一輪把 5 種模板元件改成「內部保有跟主日誌一樣的書寫／召喚／引用／回覆能力，收合只顯示名稱＋時間戳記」後，畫面仍回報崩潰。往下第一段先給出這次實際比對原型 CSS 找到的根因，再給三個修復方向讓你選 —— 這次先提案，不直接改線上程式碼。

展開後高度暴衝元件展開時，內容區塊看起來被撐到遠超過實際文字量的高度，像整塊版面垮掉。
摺疊列文字擠壓／換行收合狀態的名稱＋時間戳記列，在雙人駕駛艙（窄欄）裡偶爾看起來被裁切或擠壓。
「今天誕生的物件」偶爾顯示已刪除部分截圖仍看到 doc_object 已刪除，需要與容器問題分開追。
五種元件段落數不一Standup 4 段、1:1 5 段、會議記錄 5 段、回顧 3 段 —— 段數愈多，崩潰感愈明顯，暗示問題跟「每段各自的高度」有關而不是單一元件本身。

根因：每個 section 內文都繼承了主日誌整頁編輯器的 min-height:360px

上一輪把每個 section 的內文容器重用了原型既有的 .doc class（這是刻意的：docClick / docKey / docInput / checkTrigger / applySummon 這整套書寫引擎的事件綁定都是掛在 .doc 元素上，重用它才能讓 #召喚、@引用、Tab 縮排原封不動可用）。但原型裡 .doc 唯一的一條規則是給「一整頁的主日誌」設計的：

.doc{padding:6px 2px 40px;min-height:360px;cursor:text}

這條規則沒有針對容器層級（是主日誌還是元件內的一小段）做區分，於是元件裡「每一段」都被強制垫高到至少 360px —— 而每個模板元件有 3～5 段，全部展開時等於疊加 3～5 倍的 360px 空白，遠超過使用者實際打的一兩行字，看起來就是「整塊版面垮掉」。收合列的擠壓／換行則是次要問題，多半是 .eb-doc-bar-title 在雙欄窄版（.jc-col 只有約半個螢幕寬）下沒有跟 .eb-doc-bar-meta 搶到足夠的 min-width:0 收縮空間，兩者疊加讓畫面看起來比實際更糟。

元件段數現況：光是空段落疊加的最小高度
Standup4≈ 1,440px
1:1 檢核5≈ 1,800px
會議記錄5≈ 1,800px
回顧3≈ 1,080px

業界對可收合內容的通用建議也指向同一個方向：不要對可收合區塊套用固定的 min-height，應讓內容依實際高度自然生長（例如 Radix UI Collapsible 用 --radix-collapsible-content-height 量測實際內容高度做動畫，而不是寫死像素值）。doc_object 已刪除 那個殘留問題不在本提案範圍內，是 jcObjName 對照「今天誕生的物件」清單時的資料對應問題，會另外處理，不影響下面三個方案的取捨。

看到的現象

單一 Standup 卡片展開後，欄內捲軸捲很多頁還捲不完，四段內容中間全是空白，只有段落標題和一行 placeholder，看起來就像「壞掉」。

為什麼

每段內文都是一個獨立的 .doc 容器，原型 CSS 給 .doc 的 min-height:360px 沒有依巢狀情境調整，四段就疊加四份 360px。

會議記錄／1:1 更嚴重

5 段 × 360px ≈ 1800px，在只有半個螢幕寬的雙人駕駛艙欄位裡，幾乎不可能一次看完一則會議記錄。

主要改動 建議先做

把 additions.css 裡元件段落的內文容器改用新 class（例如 .eb-doc-secbody），只繼承 .doc 的 padding／cursor，不繼承 min-height:360px；改成 min-height:auto，只在整段完全空白時，靠 placeholder 的一行高度自然撐開，不強迫留白。

順便修

.eb-doc-bar-title 與 .eb-doc-bar-meta 補上 min-width:0／text-overflow:ellipsis，避免雙欄窄版下標題把時間戳記擠到換行。

影響檔案

只動 additions.css 一段既有規則的 class 名稱（配合 template-objects.source.js 的 renderDocSectionBody 把容器 class 從 doc eb-doc-secbody 改成專屬 class），不動 blks() 引擎、不動事件綁定，風險最低、最快能驗證是否真的解決「崩潰感」。

取捨

維持現有「每段各自一份 sec.blocks」的資料結構，5 個模板的段落標題、placeholder 完全不用改。

主要改動 結構較大

不再讓每段各自擁有獨立的 sec.blocks 陣列和獨立的 .doc 容器／獨立 focus 情境；改成整個元件只有一份攤平的 blocks 陣列，段落標題本身變成陣列裡的一個 heading block（跟主日誌的 h3 block 是同一種型別），Tab／方向鍵可以像主日誌一樣直接在段落之間穿梭。

為什麼考慮這個方向

現有做法要對「每一段」各自維護一個 BLKS_OVERRIDE 情境（見 source-patches.mjs 的 focusin 監聽），元件段數愈多，越容易出現焦點/情境對應錯誤的邊界案例；攤平成一份陣列後，一個元件只有一個情境，跟主日誌的心智模型完全一致，複雜度直接砍掉一個維度。

影響檔案

template-objects.source.js 的 createDocObject／renderDocSectionBody／DRAWERS.doc_object 需要改寫成攤平版本；DOC_METAS.secs 的用途從「陣列 key」變成「初始 heading 文字」。改動範圍比 A 大，但改完後續要再加新模板類型（例如未來的「季度回顧」）會更輕鬆。

適合

如果你預期以後還會常常新增模板類型，或希望段落之間也能互相 @引用／拖曳排序，這個方向的長期維護成本更低。

主要改動 A 或 B 之上的加值層

在 A（或 B）修好高度問題的基礎上，每個段落標題前加一個小三角形，段落可以各自收合／展開；空段落預設收合並標「· 空」，有內容的段落預設展開。

為什麼

即使高度算對了，5 段的會議記錄／1:1 一次全展開仍然偏長；讓使用者只聚焦「有寫或現在要寫」的段落，其餘收起來看標題就好，是 Notion toggle block 的標準做法，找不到內容不用捲一大串空白。

實作成本

純前端狀態（哪些段落收合）＋ CSS，不需要碰 blks()／事件引擎；可以做成 eb-doc-card 展開狀態之外，各段落再疊一層獨立的 UI 狀態，跟 A／B 都相容。

適合

1:1 檢核、會議記錄這類段數多、常常有些段落當次用不到的模板；Standup／回顧段數少（3～4 段），不一定需要加這層。

建議路線

三個方向不互斥，是漸進關係：

  1. 先做 A —— 這是實際造成「崩潰」的根因，改動小、風險低，能立刻驗證問題是否真的解決。
  2. 觀察一週實際使用情況：如果會議記錄／1:1 這種多段落模板仍然感覺長，再加 C（段落各自收合），純前端狀態、跟 A 相容，隨時可以疊上去。
  3. B（攤平成單一編輯器）先不用急，除非近期真的要密集新增模板類型，或段落間互相引用／拖曳排序變成明確需求，再評估要不要做這次較大的重構。

另外，doc_object 已刪除 的殘留問題（「今天誕生的物件」清單對不上）會另外排查，不影響上面三個方向的選擇。
