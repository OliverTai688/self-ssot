營運模組整合提案

你指出的問題是對的：工作台、專案、時間線（日曆）現在是三個平行模組，但它們其實是同一件事的三種切面。這份提案把最上層架構收斂成三個類別 —— 專案、日常節奏、行政／活動 —— 並讓日曆與 heatmap 成為橫跨三者的共用視圖。三案的差別不在畫面美醜，而在「資料模型怎麼切」與「主操作面放在哪」，這兩件事決定後面半年的擴充成本。

現況：三個模組各自為政工作台的「過去／現在／未來」、專案的工作清單、時間線的事件清單，三份資料沒有共同骨幹，同一件事要在三個地方各看一次。
現況：層級只是一個標籤時間線事件的 layer 欄位（專案／日常／行政）目前只是篩選用的 chips，沒有帶出任何結構差異 —— 但這三類的本質完全不同。
現況：沒有「是否真的發生」的紀錄節奏（standup／1:1／回顧／學習日）需要的是「有沒有照節奏跑」，現有模型只能記「有沒有排」，缺少履行狀態、質性紀錄與錄音。
現況：缺少跨類別的時間視圖時間線只有清單與日曆兩個檢視、且只分層級；沒有 heatmap 這種「看密度、看斷層」的視圖來回答「這個月是不是被行政吃掉了」。

共同前提：三個類別的本質差異

三案都建立在這張表上。差異的關鍵是「時間的形狀」：專案是「一段區間 + 里程碑」、節奏是「一條重複規則 + 每次的履行實例」、活動是「一個時間點 + 事後的回顧素材」。把它們硬塞進同一張 events 表，是目前架構最大的隱憂。

1 · 專案

「這個案子怎麼推、怎麼收尾？」
  • 時間形狀：區間（start → due）+ 里程碑
  • 層次：專案 → 里程碑 → 目標 → 任務
  • 要的視圖：流程（看板）掌握節奏、時間線（甘特）掌握時程、里程碑清單掌握交付
  • 多案並行：需要跨專案的負載與衝期檢查
  • 產物：交付物、Evidence、金流

2 · 日常節奏

「該有的節奏，這陣子有沒有真的在跑？」
  • 時間形狀：重複規則（RRULE）+ 每次實例
  • 兩種歸屬：公司節奏（standup／1:1／回顧）與個人節奏（學習日／晨寫／健身）
  • 要的視圖：日曆看排程、履行 heatmap看斷層
  • 核心欄位：履行狀態（已跑／跳過／改期）
  • 產物：質性紀錄、錄音檔、下次要帶的議題

3 · 行政／活動

「那天發生了什麼？留下了什麼？」
  • 時間形狀：一次性時間點／短區間
  • 類型：品牌日、客戶會議、旅遊、慶生、企業參訪、報稅等行政
  • 要的視圖：日曆登記、回顧牆看素材
  • 核心欄位：事前（誰參加、準備清單）／事後（紀錄、照片、錄音、文件）
  • 產物：活動回顧、對外素材、行政憑證

三個方向

核心想法：把 issue／event／專案里程碑合併成單一 node 表，用 kind 欄位區分三種型別，其餘欄位共用（日期、負責人、狀態、媒體）。導覽上把「工作台／專案／時間線」三個側欄項目收成一個「營運」模組，裡面用檢視切換器在日曆／熱力／看板／甘特／清單之間切。CRUD 只有一張會隨 kind 變形的表單：選了「節奏」就長出重複規則與履行欄位，選了「活動」就長出媒體上傳區。
適合你如果：想在兩三週內就用上統一視圖，且接受專案管理的深度先維持在現在的水準。

優點

  • 改動面積最小。現有 events 與 issues 可直接遷移，時間線的表單邏輯幾乎照搬，兩三週可上線。
  • 跨類別查詢天生簡單。日曆、heatmap、工作台都只查一張表，不需要 union 三個來源。
  • 側欄變短。工作台／專案／時間線三個項目收成一個「營運」，側欄從 8 項降到 6 項。
  • 新增類別成本低。將來要加第四類（例如「學習專題」），只是多一個 kind。

代價

  • 專案深度被壓縮。里程碑→目標→任務的三層結構只能靠 parent_id 自參照硬撐，查詢會愈來愈醜。
  • 寬表欄位稀疏。rrule 只有節奏用、end_at 只有專案用，一張表大半欄位永遠是 null。
  • 表單會愈變愈複雜。「隨 kind 變形」在三種型別還行，到第五種就會變成難維護的條件樹。
  • 權限難分。個人節奏與公司專案在同一張表，RLS 規則要寫得很小心。

核心想法：承認三類本質不同，各自給一套合身的模型與 CRUD：專案有 project → milestone → objective → task 四層；節奏有 rhythm（規則）→ session（實例） 兩層；活動有 occasion 加媒體。但三者都同步寫進一條共用的 time_spine（時間骨幹） —— 一張只存「什麼東西、哪一天、屬於誰、什麼顏色」的輕量索引表。日曆與 heatmap 只讀骨幹，因此跨類別視圖依然是單一查詢。
工作台的角色也變了：它不再是第四個模組，而是骨幹的「今天」切面 —— 自動由三軌匯流而成。
適合你如果：你希望專案管理真的長成能接多案的樣子，願意多花一輪時間把模型做對。

和現在的工作台最大差別：卡片上有軌道標籤，而且節奏與活動也會進來。「過去」欄不再只是已完成的工作，而是所有還沒收尾的東西（沒標記的節奏、沒寫回顧的活動、逾期的里程碑）。

優點

  • 模型正確。重複規則 vs 一次性事件 vs 區間＋里程碑，本來就是三種東西，分開才不會互相扭曲。
  • 專案能長大。四層結構讓你之後要接五六個案子、做跨案負載與衝期檢查都有地方放。
  • 節奏有了履行概念。session.state 是 heatmap 紅格的來源，「節奏斷了」第一次變成可查詢的事實。
  • 跨類別視圖仍是單一查詢。骨幹表扁平又小，日曆／heatmap／工作台效能好。
  • 權限乾淨。個人節奏留在 rhythm 表，用 scope 就能擋掉，不會污染專案資料。

代價

  • 多一層同步要守。骨幹是衍生資料，任何一軌漏寫就會造成日曆與來源不一致，需要 trigger ＋ 定期對帳。
  • 工期最長。三套表單、四層專案結構、節奏實例預生 —— 大約是提案 A 的兩倍半。
  • 側欄變回四項。統一視圖＋三軌，項目數沒有真的變少（但語意清楚很多）。
  • 初期資料少時會顯得過度設計。兩人規模、三個案子的情境下，四層結構可能有兩層長期是空的。

核心想法：不再有「進到某個模組去新增一筆」這件事。日曆（或熱力／甘特）本身就是主操作面，佔滿整個畫布；左邊是三條軌道的篩選欄，右邊是常駐 inspector。所有 CRUD 都在 inspector 就地完成：點空白格 → 右側長出新增表單；點任一項 → 右側變成編輯；拖拉格子 → 直接改期並即時算出衝突。模型可沿用提案 B 的三軌，但介面哲學完全不同 —— 它假設你每天打開系統的第一個動作是「看這段時間長什麼樣子」，而不是「去哪個模組找東西」。
適合你如果：你要的是「掌握節奏」的體感，而且願意接受這是三案裡前端工程量最大的一版。

優點

  • 操作成本最低。新增一筆從「開模組 → 找按鈕 → 填表 → 回列表」四步，變成「點格子 → 填 → 存」兩步。
  • 時間感最強。你想要的「掌握節奏」在這版是字面意義的 —— 打開就看見整段時間的形狀。
  • 跨類別因果一眼可見。三軌疊圖讓「專案一重、個人節奏先斷」這種模式自己浮出來。
  • 衝期檢查是即時的。拖拉當下就算，不是事後報表。

代價

  • 前端工程量最大。拖拉改期、多日事件的疊放演算法、inspector 狀態機，都是硬工。
  • 深度管理仍需另開頁。專案的四層結構、Evidence Repo、財務不可能塞進 inspector，還是要有專案詳情頁 —— 等於畫布之外仍有第二套介面。
  • 小螢幕吃力。左軌道＋日曆＋inspector 三欄在筆電上會很擠，需要設計收合。
  • 誤操作風險。拖拉即改期，必須做 undo，否則手滑就動到客戶交期。

我的建議

先做 B 的模型，先上 A 的介面，把 C 當第二階段

三案不必互斥。真正不可逆的是資料模型 —— 介面隨時能換，schema 換一次要付遷移成本。所以：

  • 第一步（2–3 週）：採用 B 的三軌模型與 time_spine，但介面先做 A 的樣子 —— 單一「營運」模組、頂部檢視切換器、一張會變形的表單。模型已經是對的，使用者只看到一個簡單的介面。
  • 第二步（3–4 週）：把三軌的專屬深度長出來 —— 專案的里程碑／目標層、節奏的 session 紀錄與錄音、活動的事前清單與回顧牆。此時側欄才從 A 的一項展開成 B 的四項。
  • 第三步（視使用情況）：再決定要不要做 C 的畫布。前兩步跑三個月後，你會清楚知道自己是不是真的每天從日曆開始 —— 如果是，C 值得做；如果你其實都從工作台的「現在」欄開始，那 C 的投資就不划算。

立刻可做、且三案都需要的兩件事：①把時間線事件的 layer 從「標籤」升級成「型別」，並補上 scope（公司／個人）；②幫節奏加上「履行狀態」欄位 —— 沒有這個欄位，heatmap 的紅格永遠畫不出來，而那正是你想看見的東西。

本檔案是靜態提案稿（可點三個頁籤切換），所有畫面為 wireframe，不含實際資料。
現有素材對照：時間線事件表單 formEvent()、工作台三段式時序欄、專案五分頁（總覽／工作／對話／Evidence Repo／財務）均已存在於 v5 runtime，三案都以延用為前提設計。
