今日議題：從「一行上的旗標」變成「可以處理的一件事」

現在的今日議題只有兩個動詞（標記、完成），綁在單一行上，沒有自己的日期，也沒有地方放討論和檔案。 這份文件先把現況的資料模型攤開、指出四個缺口與兩個順帶發現的既有缺陷，接著是七份外部產品的研究依據， 然後給三種介面提案（可點擊試操作），最後是比較與建議。

一、現況：程式碼裡的今日議題長這樣src/components/yuanzhan/v5/runtime.js

// rqFlagToday(b) —— 標記一行為今日議題 t = { id: nid('TDY'), author: DB.me, day: S.jday, // 掛在哪一天的日誌（延後時會被覆寫） blockId: b.id, // ← 單數。一個議題 = 一行 text: b.text.trim(),// ← 標記當下的文字快照，之後不再同步 at: Date.now(), doneAt?, deferred? // 全部能力就這兩個欄位 } // 動詞：rqFlagToday（建立）／rqCompleteToday（完成）／rqDeferToday（day = 明天）
缺口 1

只能綁單行

blockId 是單數，b.today 也是單數。畫面上那條「[行動] 繼續開發PersonalOS」底下三個子項， 語意上是同一件事，但系統只認得母行。沒有任何 API 讓一個議題涵蓋多行。

缺口 2

沒有自己的日期

只有 day＝「掛在哪一天的日誌」。沒有到期日、沒有提出日。 延後時 t.day = 明天 直接覆寫，議題是「被搬走」而不是「被帶著走」。

缺口 3

不能展開討論

請求（rq）有 replies[]，Thread 有 msgs[]， 文件物件有 sec.blocks。只有議題什麼都沒有——想討論只能另外發一個請求，兩件事就此分家。

缺口 4

不能掛檔案

系統其實已經有上傳（uploadFile() → R2、uploadThreadFile()、attachVoucher()）。 基礎設施在，議題沒有接上去。

順帶發現 A

右欄文字會過期

t.text 是標記當下的快照。之後把那一行改寫，右欄的議題卡仍顯示舊句子。 兩邊對不起來，而且沒有任何提示。建議一併改成讀 bOf(blockId).text。

順帶發現 B

延後會抹掉歷史

deferred 有記次數，但「原本是哪一天提出的」被 t.day 覆寫掉了。 一件被延三次的事，看不出它其實是週一就提出來的。需要 bornDay 與 carried[]。

二、研究輪次七份外部產品，五個問題

R1

「議題」到底是哪一種列？

Fellow 把會議筆記的行分成三層：Bullet（不追蹤）／Talking point（可指派、可帶到下次，沒有到期日）／Action item（可指派、有到期日、可帶到下次）。

判定：議題 ≠ 行動。它是「今天要處理掉的一段話」，要能被帶走、要能結束，但不該被逼著填專案級欄位。到期日應該是選填。
R2

討論該掛在哪裡？

Basecamp 2008 年把「檔案與留言」從 message 區搬到 to-do 本身，理由正是討論散在別處。Fellow 也是每一行從 ⋯ 開留言、留言就地顯示、可 resolve。

掛在議題本身，不要另開請求。並且議題要能被單獨連結——Basecamp 當年把「可以深連結到單一 to-do」列為同等重要的效果。
R3

一行還是一段？

Linear 支援「選取文字 → Create issue from selection」。Notion 可把選取的多個區塊 turn into page。大綱類工具（Workflowy／Tana）的預設更直接：一個節點天生包含它的子樹。

預設吃子樹，非連續多行才用明確多選。畫面上那三個縮排子項不需要任何手勢就該屬於母議題；跨段落的行才需要勾選。
R4

要不要把議題物件化？

Tana 的 supertag 把一個 bullet 變成「有欄位模板的物件」，還能帶子節點與彙總頁。GitHub 的 sub-issue 則相反地強調升格是明確動作：checklist 項目要按了才變成完整 issue。

分層。本系統已經有召喚／物件索引／參考碼——議題是唯一沒被物件化的標記。但不該每個議題都變物件，要留輕量層。
R5

討論會不會把日誌淹掉？

Notion 的留言預設顯示在右側，可切成 Minimal 只留 icon；多則回覆預設收合。Basecamp 用留言 icon 的顏色區分未讀／已讀，不展開內容。

密度要可調。日誌行預設只出現「💬 3 · 📎 2」這種計數，展開是使用者的決定，不是預設狀態。

三、研究依據可查證的外部來源

來源查到什麼對本案的意義
FellowAction items v. Talking points v. Bullets 三層行型別。Talking point 可指派、未完成可帶到下一次會議，但明確不支援到期日；Action item 才有。 「今日議題」對應 talking point 那一層：到期日選填，帶到明天是內建行為而非例外處理。
FellowComments & Reactions 任何一行（talking point／action item／bullet）都能從行尾 ⋯ 選「Add a comment」，留言就地顯示，並有「顯示已解決留言」。 行級討論是成熟做法。入口放在行尾既有的 pill 區，不需要新元件。
BasecampAttach files and post comments on to-dos（37signals） 把討論從 messages 搬進 to-do 本身；用留言 icon 的顏色表示未讀／已讀／無；同時開放深連結到單一 to-do。 附件與討論必須跟著項目走。收合狀態用計數與顏色，不是內容。議題需要自己的可引用位址。
TanaSupertags 「Supertags turn a node into a typed object with a template of fields」：tag 一下，欄位、子節點模板就生出來，並有彙總所有實例的 supertag page。 本系統的召喚＋物件索引就是同一招。議題物件化不是新機制，是把既有機制套到唯一漏掉的地方。
GitHubAdding sub-issues 清單項目可升格為完整 issue（自帶討論），母 issue 顯示進度；上限 100 個子項、8 層巢狀。 升格是明確動作而非自動。也提醒要設上限——否則一天的日誌可以長成一棵樹。
NotionComments, mentions & reminders 留言預設顯示在文字右側，可切 Minimal 只顯示 icon；多則回覆預設收合；可 resolve 並之後重開。 展開／收合要是使用者可控的檢視模式，不是每個議題各自的狀態。
LinearCreate issues 「Highlight text and click the Create issue from selection icon in the formatting bar」——選取文字直接生成 issue。 多行選取 → 建立物件，是使用者已經熟悉的手勢。浮動工具列比右鍵選單更容易被發現。

成本與風險
  • 最大的好處：討論、附件、結案五欄、參考碼、物件索引、回到來源行——全都已經寫好了，只是接上去。
  • 最大的代價：升格會把日誌那幾行換成一張卡。原文被搬進物件內文，日誌的「當天流水」語感會被切斷。
  • 風險：兩層（L1／L2）要讓人搞得懂什麼時候該升格，否則會出現一半議題是 pill、一半是卡片的混亂。
  • 風險：每日議題若都升格，物件索引會被日常瑣事灌爆。建議只有帶過 ≥1 次或有討論的才提示升格。

成本與風險
  • 日誌零成本：左欄只多一個高亮 class 與撿行模式的 ＋ 按鈕，其餘完全不動。
  • 撿行是獨有能力：A 只能在建立當下決定範圍，B 要編輯物件內文；C 隨時能加行，這最貼近日誌是「一整天長出來的」。
  • 風險：右欄目前已經有四段（回覆追蹤／今日議題／今天誕生的物件／今日脈絡）。整欄被詳情面板佔掉時，其他三段暫時看不到。
  • 風險：300px 寬放討論串偏窄，長句子會斷成很多行。可能要把右欄加寬到 340–380px。

建議：C 的骨架 ＋ A 的入口，B 當作終局但先不做

三案不是互斥的，因為它們其實解的是同一組資料模型缺口（blockIds[]、三個日期、msgs[]、files[]）， 差別只在這些東西顯示在哪裡。所以先把資料模型一次補齊，介面分階段。

不先做 B 的理由：升格成物件會把日誌那幾行換成卡片，等於改變「日誌是一天的流水」這個核心語感—— 這是產品判斷，不該由介面提案順手決定。而且 GitHub 的 sub-issue 也印證升格該是明確、少用的動作： 每天的議題大多數三天內就結束了，不值得每件都發一組參考碼。

階段 1
補資料模型

blockIds[]（吃子樹）、bornDay/due/carried[]、msgs[]、files[]。 同時修掉快照過期（發現 A）與延後抹掉歷史（發現 B）。介面先不動。

階段 2
右欄詳情面板（C）

點議題卡 → 右欄換成詳情，日誌同步高亮。討論與附件都在這裡。右欄加寬到 340px。

階段 3
行內入口（A 的 pill）

日誌行的 pill 加上計數與到期日；點 pill 直接打開右欄詳情（不是就地展開，避免日誌被撐開）。多選浮動工具列一併上。

階段 4
升格（B），視使用情況再決定

只有帶過 ≥1 次或已有討論的議題，才在詳情面板出現「升格為議題物件 ↗」。累積一兩個月再看有多少人按。

需要你決定的三件事

  • 議題要不要能指給 Lily？現在只有 author。如果要「請 Lily 處理」，那跟既有的請求機制就重疊了—— 建議議題只加「要誰看（watcher）」，真的要對方回覆還是走請求。
  • 到期日超過今天的議題，還算「今日」議題嗎？建議：到期日 ≤ 今天才出現在今日議題區，之後的進「本週」—— 但這會讓右欄多一段，需要你確認。
  • 收工檢查怎麼算？現在是「沒動的自動延到明天」。有了到期日之後， 建議改成：到期日在今天的必須處理，到期日在後面的不進收工檢查。
