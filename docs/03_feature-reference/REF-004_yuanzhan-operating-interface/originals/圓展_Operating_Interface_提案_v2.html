v2：從卡片盤點，改成情境系統

v1 回答了「缺哪些介面」，答案是一張卡片清單。但公司運轉時的思考不是「我要開哪個模組」，而是「我現在處在什麼情境」。v2 把整個系統重新組織成 7 個情境工作台，定義一套統一的導航契約（大概念 → 分頁 → 單一主操作面 + 抽屜子操作），並把日誌變成整個系統的輸入端口。

00　v1 錯在哪裡

問題一

模組導向，不是情境導向

v1 列了 24 個介面，但沒有回答「我早上打開電腦第一個看到什麼」。使用者不會先想「我要用 Evidence 模組」，他會想「這個案子該收尾了」。

問題二

卡片海

每個畫面都是一堆並列卡片。並列的意思是「你自己決定看哪個」，等於把認知成本丟回給人。專注一件事需要的是一個主操作面。

問題三

Evidence 被當成欄位

v1 把 Evidence 做成 Issue 上的附件列表。但專案收尾是一個整理與敘事的過程——像 GitHub repo 那樣有結構、有 README、有版本演化，不是一堆連結。

v2 的三個改動

  1. 導航契約統一。全系統只有一種結構：一個大概念 → 分頁子概念 → 一個主操作面 + 抽屜／彈窗子操作。任何畫面都不出現三張以上的並列卡片。
  2. 日誌升級為輸入端口。日誌裡的每一個 bullet 都可以被「賦型」成 component（Standup、Issue、Todo、Decision、Expense…），欄位自動長出來。你在寫字，系統在建物件。
  3. Evidence 升級為 Repo。專案不是被「標記完成」，是被收攏成一個可版本化、可審核的資料夾，有 README、有結構、有 tag。

01　導航契約

這一節是整份提案最重要的部分。它不是視覺規範，是一條所有畫面都必須遵守的結構規則——有了它，你才能「一次專注一件事，同時很好地穿梭在多階層概念之間」。

fig 1　三層導航契約。層級只有三層——研究顯示企業級介面的漸進揭露以三層為安全上限：常駐功能／一次互動可達／專屬區域。

反卡片三條硬規則

  • 一個分頁只有一個主操作面。需要第二個主面，就是需要第二個分頁。
  • 並列區塊上限三個，且必須是同一物件的不同面向（例如專案的「進度／成本／承諾」），不能是不相干的模組摘要。
  • 資訊密度優先於展開。列表一行就顯示完整 metadata（狀態、負責人、專案、金額、時間），不要做「點開卡片才看得到」。要看更多才開抽屜。

固定選項，不做設定

兩人公司最貴的不是功能不足，是設定過多。狀態集合、專案類型、成本類別、Size 刻度全部寫死在程式裡，不做設定頁。當某個寫死的值真的不夠用，那是一次 commit，不是一個給使用者的下拉選單。

02　核心原語：Component Block

你說的「日記可以叫出 component 進行填寫更新，也可以建立 Issue、Todo」——這在技術上是一個很明確的模型：把大綱裡的每一個 bullet 當成一個可被賦型的節點。純文字 bullet 就是純文字；打上型別，欄位就長出來，它同時變成一個可被全系統查詢的物件。

fig 2　一個 bullet 的生命週期。這個模型在 Tana 稱為 supertag：標籤不只是分類，而是「這個節點屬於哪一個資料庫」，套上去之後預設欄位自動浮現。

三條讓它不會失控的規則

  • 賦型是明確動作，不是自動偵測。AI 可以建議「這句話看起來像 Issue」，但一定要你按下去才成立。否則日誌會變成第二份待辦清單，兩邊都不準。這也正是 Handbook 04.1 說的「不要為了餵 AI 而維護第二套資料」。
  • 型別最多 8 種，寫死。超過 8 種你會記不住斜線指令，這個機制就死了。
  • 物件有唯一家。Issue 的家在專案，Expense 的家在帳本，日誌只是它誕生的地方。日誌顯示的是連結與即時狀態，不是副本。

WB6 · 容量 — 從配置到預測

你給的概念鏈 Capacity → Size → WIP → Throughput → Cycle Time → Milestone Forecast 正是流量指標（flow metrics）的標準模型。研究確認了三件事，值得寫進設計：

  • Little's Law：平均 WIP = 平均 Throughput × 平均 Cycle Time。三個數字不是獨立指標，是同一個系統的三個面。所以介面要把它們放在一起看，不是三張分開的圖。
  • 百分位需要樣本：一般建議至少 30 個已完成項目才開始談 P50/P85。兩人公司每週完成約 5 項，代表大約 6–8 週後這些數字才有意義。在那之前介面要誠實顯示「樣本不足」。
  • Work Item Age 是唯一的領先指標。Cycle Time 與 Throughput 都是落後指標，只能事後檢討；只有「這件事已經開始幾天了」能在當下救火。所以 Age 應該出現在 WB3 的「現在」欄，而不是埋在容量頁裡。

三個欄位決定整個系統成不成立

Txn.project_id 與 Txn.is_pass_through — 沒有這兩欄就算不出可分配毛利，算不出毛利就發不出獎金（契約 §9、§10）。
Issue.started_at / done_at — 沒有這兩個日期就沒有任何流量指標，Capacity Model 永遠建不起來。
TimelineEvent.derived_from — 沒有它就分不出「安排」與「承諾」，承諾會被當成一般行程刪掉。

順序的理由

WB6 容量排在最後，不是因為不重要，是因為它需要時間累積資料。流量指標在樣本不足時給出的數字比沒有數字更危險。但 Issue.started_at / done_at 必須在 S1 就存在——資料要從第一天開始收，介面可以晚半年再做。這是整份路線圖裡唯一一個「欄位先行、介面後補」的例外。

07　一句話

v1 給了你一張清單，v2 給你一條規則：一個大概念 → 分頁 → 一個主操作面 + 抽屜，七個情境各佔一個大概念，全系統共用一組被賦型的 block。你在日誌裡寫字，系統在建物件；你在專案裡收尾，系統在封存證據；你在帳本裡打一列，系統在算獎金。介面不是模組的入口，是情境的形狀。
