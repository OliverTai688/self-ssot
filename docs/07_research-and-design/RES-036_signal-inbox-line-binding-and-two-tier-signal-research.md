## 2. 管道決策：建議 LINE 單一管道

| | LINE | Telegram |
|---|---|---|
| 收（潛在訊號的來源） | 客戶與廠商的對話就在 LINE 群 —— 唯一有內容可分析的地方 | 沒有任何業務對話在這裡 |
| 發（個人推播） | 可。一對一 push，需先加好友 | 可，免費無上限 |
| 身分綁定 | 收訊息要知道「誰說的」，本來就得做 LINE 身分綁定；推播重用同一份 | 只為了推播另做一套身分 |
| 成本 | push 依**收件人數**計費；reply 不計費。輕用量 200 則／月免費 | 0 |
| 風險 | 一條公開 webhook、bot 出現在客戶群（OD-H） | 一條公開 webhook |

**建議**：LINE 同時當收與發。理由是潛在訊號非 LINE 不可，而一旦做了 LINE 身分綁定，推播就是順手的事；再養一個 Telegram 是為了省錢多維護一整套帳號綁定。

推播量估算：兩人 × 每日 2 則摘要 × 30 天 = 120 則，加上逾期即時提醒，落在輕用量 200 則內。兩條護欄讓它不會爆：

1. **只推一對一、只推給已綁定的內部成員。絕不 push 進群組** —— 群組 push 以群人數計費，而且在客戶群發話屬於對外輸出。
2. 設定頁顯示本月已用則數（LINE 有查詢 API）；到 80% 把即時提醒降級為只留每日摘要。

發送端做成 `NotificationChannel` 介面（`send(memberId, digest)`），LINE 是第一個實作。日後要加 Telegram 是多一個 adapter，不是重做。

> 註：台灣方案現為輕用量 0 元／200 則、中用量 800 元／3,000 則、高用量 1,200 元／6,000 則；官方公告 2026-11-01 起中、高用量月費調為 1,000／1,400 元，免費則數不變。

## 3. LINE 平台的硬限制（決定了流程長相）

| 限制 | 對設計的影響 |
|---|---|
| 一個群組同時只能有一個 LINE 官方帳號 | 客戶群若已有別的官方帳號，bot 進不去 → 該群只能走 `.txt` 匯出檔匯入 |
| 「允許加入群組」預設關閉 | Owner 開通時的必做步驟，設定頁要能檢查 |
| 沒有 API 能列出 bot 所在的群組、人也查不到 groupId | 只能靠 `join`／訊息事件自己記下 groupId → 需要「未認領群組」這個狀態 |
| 加入前的訊息拿不到，事後也無法重抓文字 | 綁定後才開始記錄；之前的歷史走匯出檔 |
| userId 以 provider 為範圍（同 provider 的 Login 與 Messaging channel 拿到同一個 userId） | 兩個 channel 必須建在同一個 provider，之後不能搬 |
| push 以收件人數計、reply 免費 | 綁定確認一律用 replyToken 回，不用 push |
| 媒體內容會過期 | 事件先落地回 200，媒體另抓＋重試（RES-033 已定） |
| 群組成員名單／個人資料不保證拿得到 | 一律容忍「只有 userId、沒有名字」 |

## 4. 帳號初始化：什麼叫「可追蹤的 LINE 帳號」

系統裡的 LINE 帳號分兩種，介面與權限完全不同：

| 類別 | 是誰 | 怎麼產生 | 能做什麼 |
|---|---|---|---|
| **成員帳號** | 站內成員（戴宇星、Lily） | 本人在設定頁主動綁定 | 收個人推播；他在群裡說的話歸到他的席位；有權把群組綁到專案 |
| **外部聯絡人** | 客戶、廠商 | bot 在已綁定的群裡第一次看到這個 userId 時自動建立 | 只被辨識與標示，**永不推播**；Owner 可把他對到專案的聯絡人／參與者 |

### 4.1 成員綁定流程（設定 → 我的 LINE）

```txt
① 設定頁「連結 LINE」
   → 顯示 bot 的加好友 QR ＋ 一組一次性代碼（例 YZ-4K7Q，10 分鐘有效）
② 使用者加 bot 好友，在一對一聊天室把代碼傳給 bot
   → webhook 收到：代碼有效 → 取得 lineUserId，但先不生效
③ 設定頁即時顯示「這是你嗎？」＋ 該 LINE 帳號的名稱與頭像
   → 使用者在網站按「是我」才寫入綁定
④ bot 用 replyToken 回「已連結」；設定頁出現「傳一則測試推播」
```

- 第 ③ 步的網站確認是防冒用的關鍵：代碼外流時，冒用者的名字頭像會出現在本人畫面上，本人不按就不成立。
- 狀態：`未連結` → `等待代碼` → `待確認` → `已連結` → （封鎖 bot 時）`推播失效`。封鎖由 `unfollow` 事件得知，設定頁要顯示，否則使用者會以為還在收。
- 「可追蹤」的定義＝已連結且未封鎖。只有這個狀態的成員出現在推播名單裡。
- 個人推播偏好放同一頁：時段（預設 09:00／18:00）、內容（逾期／待我回覆／每日摘要）、解除連結。

**替代方案（未選）**：LINE Login。優點是免打代碼、身分由 LINE 驗證；代價是多一個 Login channel 與 OAuth callback，而且加好友仍是另一步。兩人團隊先用代碼＋網站確認；哪天要「用 LINE 登入網站」再升級，userId 相同、綁定資料不用重做。

## 5. 群組綁定到專案

### 5.1 流程：在網站上認領，不在客戶面前打指令

```txt
① 專案 → 設定 → LINE 群組 →「連結 LINE 群」
   → 說明卡：把「圓展 OS」邀進群組（附 bot ID 與 QR）
② 成員在 LINE 把 bot 邀進群
   → join 事件：記下 groupId、群名、頭像、人數，狀態＝未認領
   → bot 不發言
③ 網站即時出現「新群組：〈群名〉· N 人 · 剛剛加入」
   → 選擇用途（客戶群／內部群／廠商群）→ 按「綁到這個專案」
④ 建立 LINE_MIRROR 頻道，從這一刻起的訊息進專案聊天室（唯讀）
```

- 認領發生在網站上，所以**客戶群裡不會出現任何指令或代碼**。
- 誰能認領：對該專案有管理權限、且自己的成員帳號已連結的人。伺服器端另外檢查「邀 bot 進群的人或群內至少一位發話者是已連結成員」，擋掉「別人把 bot 拉進無關群組，再被誤認領」。
- 捷徑（選用）：已連結成員在群裡傳專案代碼直接綁定。只建議用在內部群。
- **未認領期間不保存訊息內文**，只留群名、人數、訊息數。72 小時沒人認領 bot 自動退群。理由：任何知道 bot ID 的人都能把它拉進群，未經認領就存對話等於收了不該收的東西。
- 訊號頁右欄與專案設定都會顯示未認領群組 —— 「有個群在等你認領」本身就是一個需要注意的狀況。

### 5.2 一個專案多個群

| 關係 | 規則 |
|---|---|
| 專案 → 群組 | 一對多。每個綁定＝專案聊天室裡一個 `LINE_MIRROR` 頻道 |
| 群組 → 專案 | 同一時間只屬於一個專案（主專案） |
| 用途標籤 | 客戶群／內部群／廠商群，綁定時必選。它決定潛在訊號怎麼判讀（客戶問我們 ≠ 內部閒聊）以及預設是否開啟 AI 分析 |
| 一個群談好幾個專案 | 不做群組多綁。改在**採納潛在訊號時可改專案**（預設帶主專案） |
| 解除綁定 | 停止收新訊息、歷史保留唯讀、可選擇讓 bot 退群。不刪資料 |
| 換專案 | 解除後重新認領；舊訊息留在舊專案，不搬 |

專案設定頁的清單欄位：群名、用途、狀態（同步中／bot 已被移出／已解除）、綁定人與時間、訊息數、最後一則時間、AI 分析開關。

### 5.3 群組揭露

bot 會出現在群組成員名單裡，客戶看得到。Owner 已同意（D3）：**綁定時說一句揭露，之後保持沉默**。

更正初版的一個技術錯誤：初版寫「用 replyToken 發」，但認領發生在網站上，當下沒有可用的 replyToken（它只在收到事件後短時間內有效）。因此揭露是**綁定當下對該群的一次性 push**，會用掉「群人數」則額度（8 人的群＝8 則，每群一輩子一次）。認領的確認框要寫出這個數字；額度不足時改為在該群下一則訊息進來時用 reply 補發，並在專案設定標示「揭露尚未送出」。

揭露文字屬於對外輸出，定稿在 `AUT-010` §5，由 Owner 核准後才能送。

## 6. 兩層訊號

### 6.1 定義

| | 確定訊號 | 潛在訊號 |
|---|---|---|
| 來源 | 日誌與結構化紀錄：`?@人` 請求、今日議題、`/doing` `/done`、現有七條規則 | LINE 群訊息的分析結果 |
| 產生方式 | 規則，從你本來就在填的欄位推導 | 兩條規則自動偵測；AI 判讀只在人主動發起並確認送出後才發生 |
| 可信度 | 一定成立，每筆可指回一行日誌或一筆紀錄 | 可能錯，每筆必須附原話與信心 |
| 進逾期橫幅／擋收工 | 是 | **否** |
| 計入側欄徽章 | 是 | 否，另計一個「待確認」數 |
| 個人推播 | 逐筆 | 只推數量（「3 則 LINE 訊號待確認」），不推內文 |
| 需要人做的事 | 處理它 | 先判斷它是不是真的 |

核心規則：**潛在訊號在人按下採納之前，不產生任何義務、不改任何狀態。** 這跟 Handbook 04.4（Agent 只發訊號）與 `AGENTS.md` §11（AI 產出是待審提案）是同一條線。

### 6.2 潛在訊號的種類（第一版四種）

| 種類 | 例句 | 採納後變成 |
|---|---|---|
| 對方提問未回 | 「報價單可以分兩期付嗎？」之後我方 N 小時沒回 | 回覆追蹤的一張卡，計時從那則 LINE 訊息的時間起算 |
| 承諾與期限 | 我方：「週五前把問卷初稿給您」 | 任務或今日議題，帶期限 |
| 條件變更 | 「那就改成分兩期」「範圍加上律師那一塊」 | 決議紀錄／承諾紀錄，標示待寫回合約或報價 |
| 交付物到了 | 對方傳來檔案、簽回的文件 | 檔案歸到專案資料夾的待整理 |

每筆潛在訊號攜帶：原話（可點回該則訊息）、群組與發話者、時間、判讀種類、建議專案、建議負責人、建議期限、依據（規則／AI）、信心。

### 6.3 處理動作（四選一，都留紀錄）

| 動作 | 結果 |
|---|---|
| **採納** | 轉成確定訊號（上表右欄）。來源永久連回 LINE 訊息；採納時可改專案、負責人、期限 |
| **併入既有** | 這件事日誌裡已經有了 → 把 LINE 原話掛到既有的請求／任務當佐證，不產生第二筆。系統偵測到相似的會主動建議 |
| **忽略** | 必選原因：不是請求／已處理／與專案無關／判讀錯誤。原因用來調整規則 |
| **稍後** | 明天再出現 |

結案也是提案：採納的「對方提問未回」之後若我方在 LINE 回了，系統提示「看起來已回覆，要結案嗎？」，仍由人按。

### 6.4 潛在訊號的兩個產生途徑（Owner 2026-10-12 定案）

**途徑一：規則，自動，在系統內執行。** 不送任何內容到外部。

- 「最後一則是外部的人、內容是問句、已過 N 小時沒有我方發言」
- 「@ 到已連結的成員」

同一頻道安靜 10 分鐘後才評估一次，避免把「好」「謝謝」當成事件。這是 S3a，不需要模型。

> 這一條是本文件對 Owner 回覆的解讀：Owner 對 D4 的指示針對的是「送到 AI 分析」。規則偵測不外送，故維持自動。若 Owner 要它也改為手動，移除排程即可，其餘不受影響。

**途徑二：AI，手動，四個關卡。** 沒有任何自動或排程的 AI 分析；原提案的「逐群開關、內部群預設開」作廢。

```txt
① 選取      人選專案、群組、時間區間 → 列出這段對話
② 去識別化  系統用規則遮蔽（不靠外部 AI）→ 產生「將送出的版本」
③ 人工確認  人逐處檢查、可補遮蔽或排除整則 → 按下確認
④ 送出分析  伺服器只送確認過的那一份 → 結果在本機還原代號 → 進潛在訊號
```

**① 選取**

- 入口兩個、工作區一個：訊號頁的「對話分析」分頁；專案聊天室 LINE 頻道上的「分析這段對話」（帶著專案、頻道與區間跳進同一個工作區）。
- 區間：今天／昨天／過去 7 天／自上次分析以來／自訂起訖；也可在聊天室點兩則訊息當起點與終點。
- 顯示則數、發話者人數、約略字數。上限每次 500 則、區間 31 天。
- 誰能發起：對該專案有管理權限的人。

**② 去識別化（規則式，全程在本系統內）**

| 類別 | 做法 | 送出時長這樣 |
|---|---|---|
| 發話者 | 依群組用途與是否為已連結成員給穩定代號，同一次分析內同一人同一代號 | `我方-1`、`客戶-A`、`廠商-A` |
| 已知名稱 | 字典比對：群成員顯示名稱、專案參與者、客戶與公司名、專案名、工作區自訂遮蔽詞 | `〔人名1〕`、`〔公司A〕`、`〔專案A〕` |
| 聯絡方式與證號 | 樣式比對：手機／市話、Email、網址、LINE ID、身分證字號、統一編號、銀行帳號與卡號、地址 | `〔電話〕`、`〔Email〕`、`〔統編〕`… |
| 金額與日期 | **預設保留**（判讀承諾與條件變更需要它）；每次分析可切換為遮蔽 | 原樣，或 `〔金額〕` |
| 圖片、影音、語音、檔案 | 一律不送，只留佔位；檔名遮蔽 | `〔圖片〕`、`〔檔案〕` |
| 貼圖、系統訊息 | 略去 | — |

誠實的限制：**規則抓不到字典裡沒有的名字**（暱稱、沒登錄過的第三方）。所以 ③ 不是形式，是真正的控制點。兩個輔助：帶稱謂的字串（「X 先生／小姐／老師／會計師／律師／代書」）標為「疑似人名，請確認」；人在 ③ 補遮蔽時可選「記住」，加入工作區遮蔽詞，下次自動抓到。

不用外部 AI 來做去識別化 —— 那等於先把原文送出去，與這道關卡的目的相反。

**③ 人工確認**

- 左原文、右送出版本並排。遮蔽處標色，點一下可還原，框選任意文字可補遮蔽，每則可整則排除。
- 上方摘要：送出幾則、約幾個字、遮蔽幾處（各類別數量）、還有幾處「疑似人名」未處理。
- 右欄顯示的就是實際送出的全文，沒有另一份看不到的內容。
- 確認後若再改任何遮蔽，確認失效，要重新確認。

**④ 送出與結果**

- 送出的內容由伺服器依「訊息 id ＋ 遮蔽決定」重新組出，**不採用瀏覽器傳上來的文字**，並記下內容雜湊。這保證送出的與確認的是同一份。
- 一次請求、模型沒有任何工具、看不到資料庫。回傳必須符合固定格式（種類、指向哪幾則、摘要、建議期限、信心），不符合就整批丟棄。
- 代號對照表只留在伺服器，用來把結果對回真實的訊息與發話者；它永遠不送出。
- 結果成為潛在訊號，依據標「AI」，連回這一次分析。之後與規則產生的走同一套分流（§6.3）。
- 對話內容是不可信輸入（客戶訊息裡可能寫著「忽略以上指示」）。防線是：模型沒有工具、輸出只當資料、任何結果都要人採納才生效。

**分析紀錄**（同一分頁下方的表格）：時間、專案與群組、區間、發起與確認的人、送出則數、遮蔽數、產生幾則潛在訊號、其中採納幾則。採納率是日後判斷這個功能值不值得的依據。

同一段對話重複分析不會產生重複的潛在訊號（以訊息 id 集合去重）。

## 10. 捨棄的做法

| 做法 | 為什麼不要 |
|---|---|
| Telegram 推播＋LINE 只收 | 兩套身分綁定，省下的只有每月 0–800 元 |
| 把摘要 push 進群組 | 依群人數計費，而且是在客戶面前的對外輸出 |
| 在群裡打指令完成綁定（當主流程） | 客戶看得到；網站認領做得到同樣的事 |
| 一個群綁多個專案 | 每則訊息都要猜屬於哪個專案；改在採納時指定即可 |
| LINE 訊息直接變成確定訊號 | 判讀會錯，錯的訊號擋收工會讓人不再信任整個訊號頁 |
| 自動或排程的 AI 分析（含初版的「逐群開關」） | Owner 否決：送出前必須有人選範圍、看過去識別化結果並確認 |
| 用外部 AI 做去識別化 | 等於先把原文送出去 |
| 送出瀏覽器傳上來的確認稿 | 無法保證送出的與人看到的是同一份；改由伺服器重組並記雜湊 |
| 未認領就先存訊息 | 任何人都能把 bot 拉進群，等於收下無關的對話 |

## 11. 風險與停止條件

| 風險 | 處置 |
|---|---|
| 公開 webhook 被偽造請求 | `x-line-signature` HMAC 驗證不過即丟棄；原始事件先落地再處理 |
| bot 被拉進無關群組 | 未認領不存內文、72h 自動退群 |
| 客戶對話屬個資 | 保留期限、刪除路徑、誰看得到，寫進 `AUT-010` |
| 推播額度用完 | 用量顯示、80% 降級、額度用盡時設定頁明示「本月推播已停」而不是靜默失敗 |
| 潛在訊號太吵 | 自動的只有兩條規則；忽略必填原因；以採納率決定是否擴大 |
| 去識別化有漏網 | 規則抓不到字典外的名字 → 疑似人名提示、人工覆核是必經關卡、補遮蔽可記住；不宣稱「已完全去識別化」，介面用語是「已遮蔽 N 處，請確認」 |
| 客戶訊息夾帶對模型的指示 | 模型無工具、輸出驗格式、結果只是待採納的提案 |
| 客戶群已有其他官方帳號 | bot 進不去，介面直接說明並導向 `.txt` 匯入 |

**停止條件**：（`AUT-010` 與揭露文字已於 2026-10-13 核准，前兩條解除。）模型供應商未指定前不把任何 LINE 內文（即使已去識別化）送出；任何一次 AI 分析都必須有一筆人按下確認的紀錄，沒有例外路徑。
