## 1. Purpose

The owner is asking for two connected things, at two different altitudes:

1. **A new module-level surface**: every domain module (as scoped by the attached screenshot: 工作/研究/商會/財務/生活/公司) should expose a 檔案庫 (File Library) tab and a 媒體庫 (Media Library) tab. Inside a module these are **read/export surfaces only** — view, open, download/export — never an upload entry point.
2. **A classification/routing model underneath it**: the single upload/ingestion entry point stays AI Input's own 檔案庫/媒體庫 (built this session — `FileLibraryPage`, `MediaLibraryPage`). After AI processing, each file or media item gets classified into **one or more** modules. That routing must be visible back on the AI Input side as a label/tag per item ("已分類：工作、商會").

This document audits whether either capability exists today, grounds the design in this repo's own established precedents (`ARC-012`'s module subpage contract, `RES-009`'s tab-parity contract and `ModuleOperatingShell`, `ARC-030`'s resource-index BFF shape, `RES-012`'s already-designed "target module checkboxes" pattern, and `SCH-002`'s asset registry proposal), and converts the gap into an executable backlog. No runtime code is changed in this document.

## 4. Key Finding: Two Coupled Gaps, One Root Cause

Both gaps trace to the same root cause: the File Library and Media Library were designed (this session, and in the prior `AIINPUT-LIB-001`/`RES-006` work) as **AI Input-local** surfaces — a place to browse what's been ingested and reference it into the current chat. Neither was designed with "this same item should also be visible, read-only, from inside the module it belongs to" in mind, so the data model only needed to answer "where does this show inside AI Input," not "which modules does this belong to." The owner's ask is the first requirement that needs the second question answered, and it needs it answered as a **set**, not a single value, because a single PDF (e.g. an ESG report) can legitimately be relevant to both 工作 and 商會 at once.

This is structurally the same shape as `RES-009`'s "maturity inversion" finding: a capability (module-level resource surfacing) that `ARC-012`'s own module blueprint gestures toward ("primary operation surface" per module) but never named for library assets specifically, so it was never built anywhere, not even in the five modules that already have the fullest tab treatment (`self/chamber/finance/life/company`).

### Round 1 — Local code/PRD fit
Completed in §2–§4: confirmed `ARC-012`/`RES-009` do not name this surface, confirmed zero modules have it, confirmed the only existing classification field is single-value and inconsistent between `FileAsset` and `MediaAsset`.

### Round 2 — Comparable pattern
Two classes of comparable pattern were checked against this repo's own precedent, not fetched fresh, because a directly-applicable in-repo precedent already exists and was owner-approved:

- **This repo's own `RES-012`** already designed and the owner already accepted a "target module checkboxes" (allowed target modules, plural) interaction for source-connector default routing. Reusing the same interaction shape for asset-level classification is the strongest possible internal consistency argument — the owner has seen and approved this exact multi-select shape once already, just one layer up the pipeline.
- **External reference (already synthesized in `RES-002` §3, not re-fetched):** Google Drive's own file model allows one file to have multiple parent folders (multi-parent), and Notion's database "relation" property lets one page belong to many databases via multi-select — both are the same underlying pattern the owner is asking for (one asset, many logical locations), and both back it with a join/relation table rather than a single string column, which is the same conclusion `SCH-002`'s existing `SourceAssetLink` junction-table style already models for asset-to-asset links.

No new external fetch was needed: the repo's own `RES-012` precedent plus `RES-002`'s already-synthesized external references are sufficient and directly on point.

### Round 3 — Data/BFF/API boundary
Confirmed via `src/lib/contracts/*.ts` grep (§2): `targetModule: string` (singular) is used pervasively across `agent-operation-api`, `agent-task-message-bus`, `module-agent-command-catalog`, and every `ai-input-source-workflow-*` contract. A naive `moduleRefs: ModuleKey[]` array field would be the first many-to-many module relationship in the codebase and would sit inconsistently next to every other singular `targetModule`. The reconciling design (§6) keeps every individual link row singular (`{ assetId, moduleKey }`), and lets multiplicity come from having multiple rows — consistent with `SourceAssetLink`'s existing junction-row style and with every other contract's singular-`targetModule` convention. This avoids introducing a second modeling convention.

### Round 4 — Risk/auth/public-output boundary
Confirmed via `AGENTS.md` §11 and `ARC-012` §8: routing an asset's *metadata* into Finance/Life/Company is not itself a "final write" in the sense §11 restricts (no financial figures, personal health data, or strategy content is being written — only a classification tag), but it does determine what an owner sees when they open one of those high-risk modules' new library tab, and a wrong or silent AI classification there would be misleading in a way that matters more than in `work`/`research`/`chamber`. The resolution (§6) is a confirm-gate specifically for Finance/Life/Company/Client-Portal-adjacent routing, not a blanket approval requirement for all six modules — this keeps the risk-scoped part narrow instead of over-applying `AGENTS.md` §11 everywhere.

## 6. Recommended Standard

1. **Module-side tabs are read/export-only, never an upload entry point.** Add 檔案庫 and 媒體庫 as two new tabs (or two sub-tabs under one "資源" tab) to each of the six screenshotted modules. They render a **filtered, read-only variant** of the already-built `FileLibraryPage`/`MediaLibraryPage` components — reuse, do not fork: add a `mode: "full" | "module_readonly"` prop that hides the upload button and every mutating action (rename, tags, archive/delete, move-workspace, create/update snapshot) and keeps only `reference`/`open_source`/`view_info`/`view_versions`/`view_references` plus a new `download`/`export` action id. This directly satisfies "不用進行上傳，只有檢視和下載匯出."
2. **Do not add a many-to-many array field in isolation — model it as link rows, matching the repo's existing `targetModule: string` convention.** Introduce a conceptual `LibraryAssetModuleLink { assetId, assetKind: "file" | "media", moduleKey: ModuleKey, classificationSource: "ai_suggested" | "human_confirmed", confirmedAt?, createdAt }` shape (mock-mode: a plain array of these link objects held alongside the existing `libraryFiles`/`libraryMedia`-equivalent state, no schema change yet — this repo's established caution per `DBS-002`/`SCH-003`/`MIG-003`, same interim-step pattern `RES-006` §4.1 used for source conversation threads). Each link row keeps `moduleKey` singular; multiplicity is "many rows for one asset," not "one array field." On the client, derive `moduleRefs: ModuleKey[]` per asset by grouping link rows — this gives call sites the ergonomic array view without breaking the repo-wide singular-`targetModule` shape at the model layer.
3. **Replace `FileAsset.workspaceLabel?: string` with the link-row model, and give `MediaAsset` the same field for the first time.** `FileWorkspaceDialog`'s single-select becomes a multi-select checkbox list (reusing exactly the interaction shape `RES-012` already designed and the owner already approved for connector-level target-module routing — do not invent a new interaction pattern). Rename the dialog from "移動至 Workspace" (implies exclusive move) to "分類至模組" (classify into module(s)) to match the new semantics.
4. **AI Input's own 檔案庫/媒體庫 rows must show the routed module(s) as a label.** Add a small badge/chip row per asset (e.g. "已分類：工作、商會" or an `AI 建議` badge before confirmation) fed by the same link rows — this directly satisfies "然後可以在AI匯入的檔案庫和媒體庫的標籤看到."
5. **Gate high-risk module classification behind an explicit confirm step; low-risk modules can auto-apply with a visible AI-suggested badge.** For `work`/`research`/`chamber`, an AI-suggested classification link row can be created directly (status `ai_suggested`) and shown immediately in that module's read-only library tab with a "AI 分類" badge, editable via the same multi-select dialog. For `finance`/`life`/`company` (per `AGENTS.md` §11), an AI-suggested link row must not appear in that module's library tab until a human confirms it (status flips `ai_suggested` → `human_confirmed`); until then it is visible only inside AI Input's own library with a pending badge. This is a narrow, scoped application of §11 — it does not require approval for `work`/`research`/`chamber`.
6. **Reuse `ARC-030`'s resource-index BFF shape for the eventual module-scoped read/list contract**, rather than inventing a new list/filter/detail-drawer contract specific to libraries. The module-scoped library tab is, structurally, `ARC-030`'s resource index filtered by `moduleKey`, with row actions limited to `reference`/`open`/`download` instead of the fuller Work-first action set.
7. **Scope decided (§0A):** `self` is in scope (seven modules total: work/research/chamber/finance/life/company/self); `ai-input`/`inbox`/`dashboard`/`workflow` are confirmed out of scope and do not need a second, module-scoped library.

## 7. Gap Findings

1. No module (of the six screenshotted) has a File Library or Media Library tab; `ARC-012`'s module blueprint table (§6) does not name this subpage type at all, so there is no existing contract to simply "finish rolling out" the way `RES-009` could for the resource/agent/records triad.
2. The only classification field that exists anywhere (`FileAsset.workspaceLabel?: string`) is single-value and human-set only — it cannot represent "this file belongs to both 工作 and 商會" today.
3. `MediaAsset` (built this session) has no classification field at all — it is a strictly newer gap than the File Library's, since it didn't even inherit the single-value version.
4. The repo-wide `targetModule: string` convention (used in every agent/workflow contract) would be broken by a naive array field; no prior design in this repo reconciles "one asset, many modules" with "every contract uses a singular target." §6 point 2 resolves this via link rows, but nothing currently implements it.
5. `SCH-002`'s formal (unmigrated) schema proposal only has `SourceAsset.moduleHint?: string` (singular) and an asset-to-asset `SourceAssetLink` (not asset-to-module) — the formal schema layer would need a new junction table (`LibraryAssetModuleLink` or similar) before any real-data cutover, which is not yet reviewed or approved.
6. No confirm-gate distinction exists between low-risk (`work`/`research`/`chamber`) and high-risk (`finance`/`life`/`company`) auto-classification — without one, an AI mis-classification could silently appear inside a high-risk module's read-only tab, which `AGENTS.md` §11 exists specifically to prevent for final writes and should extend to here by analogy.
7. `RES-012`'s "target module checkboxes" interaction is designed and owner-approved but scoped to source-connector defaults, not yet reused at the individual-asset level — reusing it (rather than inventing a new interaction) is the correct move but has not been done.

## 9. Rejected Alternatives

- **Keep `workspaceLabel` as a single string and just add it to `MediaAsset` too.** Rejected: does not meet the owner's explicit "一個或多個模型" (one or more modules) requirement; would need to be redone immediately.
- **Add a raw `moduleRefs: ModuleKey[]` array field directly on `FileAsset`/`MediaAsset` with no link-row model underneath.** Rejected: breaks the repo-wide singular-`targetModule` convention used in every agent/workflow contract (`§2`, `§5` Round 3), and would need a disruptive rework once `SCH-002`-style formal persistence is approved, since `SourceAssetLink`'s existing junction-row style already shows the reconciling pattern.
- **Build a brand-new bespoke per-module library component instead of reusing `FileLibraryPage`/`MediaLibraryPage` in a read-only mode.** Rejected: duplicates ~600 lines of already-proven, just-built UI; a `mode` prop is the smaller, DRY change and matches this repo's "reuse over reinvention" precedent (`RES-009` §10).
- **Invent a new multi-select interaction for module classification.** Rejected: `RES-012` already designed and the owner already approved a target-module-checkboxes interaction for the adjacent connector-settings problem; reusing it is both less work and more consistent than a new pattern.
- **Apply the human-confirm gate uniformly to all six modules.** Rejected: `work`/`research`/`chamber` have no `AGENTS.md` §11 high-risk designation; requiring manual confirmation everywhere would add friction the owner did not ask for and is not justified by the risk rules. Scoped narrowly to `finance`/`life`/`company`.
- **Roll out to all six modules (and `self`) in one task.** Rejected: same reasoning as `RES-009`'s `MODSHELL-005` — pilot on two modules first (`MODLIB-005`), get a scope decision on `self`/infra modules (`MODLIB-006`), then roll out (`MODLIB-007`), so a design mistake is caught before it is copied six times.
- **Treat this as purely a UI tab-parity question, ignoring the data-model gap.** Rejected: the owner's second sentence explicitly requires classification and label visibility, which cannot be satisfied by a UI-only change — the link-row model (§6.2) is a required part of the artifact, not optional scope creep.
