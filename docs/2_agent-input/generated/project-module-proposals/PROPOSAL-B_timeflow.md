## 0. 一句話

**專案頁的主幹是一條時間流**，回答「這個案子到今天為止發生了什麼」；五大資源從側抽屜進入，時間流本身不被切成分頁。

刻意的取捨：**檔案的多層整理不放進時間流**。時間流只記檔案事件，整理另有「整理模式」與抽屜裡的完整資料夾樹。

### 為什麼是時間流

1. 五大資源裡有三種本質上就是時序的：聊天室（訊息流）、會議（一場一個時點）、專案本身的進展（提案→接案→執行→驗收→結案）。
2. 這個系統已經把「時間流」訓練成 Owner 的既有心智模型：日誌的雙人駕駛艙、`journal-review` 的連續敘事、`jcTimeline()` 的今日脈絡（含補記分區）、物件索引的時間軸檢視。`journal-timeline-backdating-decision.md` 甚至已經把「掛在哪一天」與「真的何時寫的」分開處理過一次——這套區分可以原封不動搬到專案時間流。
3. 五大資源各自是分頁的話，「這個案子發生了什麼」這個問題沒有任何一頁能回答；而這正是 Owner 在 weekly sync 上拿「01.共好玟化網站」當議題標題時，心裡要的那個東西。

## 1. 時間流的事件粒度與入流規則

### 1.1 一則 ＝ 一個事件，不是一次操作

> 時間流回答的是「這個案子到今天為止發生了什麼」。所以**一則＝一件在專案外部看得見的事**，而不是一次點擊、一次存檔、一則訊息。

這條定義是整個提案的地基。它直接決定了下面兩張表。

### 1.2 進流（10 類）

| 事件類 | 粒度 | 備註 |
|---|---|---|
| 期 | 一期的開始 ＝ 一個**期分隔器**，不是一般事件 | 全寬卡片，見 §3 |
| 階段 | 階段切換（執行→驗收→執行…）＝ 一條 sticky 小標 | 同一期內可重複 |
| 里程碑 | 達成／到期／逾期 | 「日期待補」的里程碑**不進流**（沿用既有語彙，刻意不猜日期） |
| 會議 | **一場＝一則**。夾內四件套摺在那一則裡，不逐檔進流 | 展開才看材料 |
| 合約／報價 | 簽署、回簽、報價有效期到期 | 12 摸摸的 2026-10-30 就是一則 |
| 金流 | 請款、收款、尾款逾期 | 金額不確定時寫「待補」 |
| 檔案 | **一批＝一則**（同一次上傳／同一資料夾／同一天合併）。只記「進了收件匣」「歸檔到哪」「改成對客戶可見」 | 逐檔列在展開區 |
| 整理 | **一次整理動作＝一則摘要** | 整理在整理模式裡做，流上只留結果 |
| 對話 | **一天＝一則折疊摘要**；被 ⚑標成決議 或 ↑升級成任務 的訊息才單獨成一則 | 見 §1.4 |
| 外部缺口 | 已知存在、但不在系統裡的約定 | 例如 01 的「LINE 上談定分兩期」 |

### 1.3 不進流（5 類）

- 單則聊天訊息（除非被標成決議或升級成任務）
- 檔案改名、搬移、刪除等整理動作的逐步操作
- 資料夾的建立與重整（結果以一則整理摘要呈現）
- 文件草稿的每一次編輯、瀏覽、下載
- 任務在看板上的欄位移動（只有里程碑層級的完成才進流）

### 1.4 聊天不會淹掉流的三道閘

1. **一天折疊成一則** —— 「專案聊天室 · 3 則」，展開才看訊息。
2. **只有被標記的訊息單獨成一則** —— 沿用日誌既有的 `?@人` / `@人` / `!今天` 手勢語彙（`journal-mention-reply-decision.md`）：在訊息上標 ⚑決議 或 ↑任務，那一刻才在流上長出獨立的一則。
3. **篩選列可以把「對話」整個關掉** —— 關掉之後骨幹（期／里程碑／會議／合約／金流）仍然完整。

這三道閘的理由是：聊天的**量**與它對「這個案子發生了什麼」的**資訊密度**不成比例。日誌已經用「行內留言收在那一行底下」解過同一個問題，這裡沿用同一個收攏手法。

### 1.5 兩個時間概念不混（直接沿用既有決策）

`journal-timeline-backdating-decision.md` 已經定過：

```
d（on_date） 這件事掛在哪一天 —— 排序主鍵
at（occurred_at） 真正寫下的時刻 —— 補記判斷
```

專案時間流完全沿用：`at` 與 `d` 不同天的事件（例如今天回頭補 4 月的會議紀錄）排在當天序列之外的「事後補記」分區，每列印真實日期。**不需要新的資料欄位語意，`OperatingAsset.filedAt`、`Occasion.createdAt`、`OperatingDayLog.occurredAt` 的既有形狀就是同一招。**

## 2. 五大資源各自落在哪

| # | 資源 | 在時間流上 | 在側抽屜裡 | 理由 |
|---|---|---|---|---|
| ① | 每個專案獨立聊天室 | 一天一則折疊摘要 ＋ 被標記的訊息獨立成則 | **對話抽屜**：頻道清單 ＋ 完整訊息串 ＋ 兩條升級路徑（訊息→任務、結論→決議） | 聊天本質是時序的，但量太大；折疊是唯一能同時保住「在流上看得到」與「不淹掉流」的做法 |
| ② | 雲端硬碟多層資料夾 CRUD | **只有檔案事件**（進收件匣／歸檔到哪／改成對客戶可見），一批一則 | **硬碟抽屜**：完整多層樹、可展開收合、收件匣是第一個節點 ＋ **整理模式**（全幅） | 整理是空間性的工作，不是時序的。見 §4 |
| ③ | 工作區：期／階段／里程碑／TODO 與審核任務 | **時間流的骨幹**：期分隔器、階段 sticky 標、里程碑事件 | **工作計劃抽屜**：期→階段→里程碑→任務 四層完整結構，TODO／REVIEW 兩種任務型別 | 「什麼時候發生」在流上，「結構長什麼樣」在抽屜 |
| ④ | LINE 群導入 | **只有一種**：外部缺口事件（已知存在、但不在系統裡的約定） | **停用入口 chip**，不可點，title 寫明原因 | PLN-075 OD-H 本階段不做；技術上也讀不到 bot 加入前的歷史訊息 |
| ⑤ | 會議資料區 | **一場＝一則**，展開看四屬性 ＋ 四件套 | **會議抽屜**：時間序清單，每場標四件套齊缺 | 會議天生是時序的，它在時間流上是原生公民，抽屜只是「同一批東西的另一種排法」 |

**關鍵結構判斷：資源不切分頁。** v5 現況是「專案 · 總覽／工作／對話／Evidence Repo／財務／里程碑」六分頁，資源之間的關聯靠使用者自己記。B 把這六個切面壓成一條流 ＋ 五個抽屜：**流是主幹，抽屜是深潛**。抽屜用 overlay 而不是第二欄，因為第二欄會把時間流壓窄到讀不下去（1440 寬時流本身就已經是 860px 的閱讀寬度）。

## 3. 「期」怎麼在時間軸上表達

這是 B 相對於 A、C 的最大結構紅利：**時間流天然能表達「二期從哪一天開始」**。

### 三個層次，三種視覺

| 層次 | 元件 | 行為 |
|---|---|---|
| **期（ProjectPhaseCycle）** | **期尺**（頁首）＋ **期分隔器**（流上） | 期尺是橫向卡片列，點一下只看那一期；期分隔器是流上的全寬斷點卡，寫明 `期 2 · 官網第二版（修改需求）  2026-08-08 起`、合約、金額、四個階段 |
| **階段（ProjectPhaseNode）** | 流上的 **sticky 小標** `● 階段 執行 期 2` | 階段切換時插入一條；同一期內 `執行→驗收→執行` 重複就插三條，**不會退化成平面 enum** |
| **里程碑／任務** | 一般事件卡／工作計劃抽屜 | 里程碑在流上，任務在抽屜 |

### 為什麼期分隔器比下拉選單好

`03.幸福文齡網站` 的二期是從 2026-09-19 的「第二次修改需求書」開始的。在分頁式介面裡，這件事只能寫成一個 `phaseRound: 2` 的欄位值；在時間流上，它是**一條橫在流中間、看得見日期的線**——而這條線的左右兩邊，事件的性質確實不同（左邊是建置，右邊是改版）。Owner 不用學任何新概念就讀得懂。

### 加三期的成本

`RES-033 §4` 已定：插一列 `ProjectPhaseCycle` ＋ 一次 UPDATE 把結案移過去，**不需要 migration、不需要改 enum**。在 B 的介面上，這等於期尺多一張卡、流上多一個分隔器，**渲染邏輯一行都不用改**（分隔器是由 `event.cyc` 的變化推導的，不是寫死的）。

### 推導不存

「現在走到哪」＝最小未 DONE 的 `(cycle.ordinal, stage.ordinal)`，不另外存欄位。期尺上的色段（綠＝done／藍＝cur／灰＝todo）就是這個推導的結果。

## 4. 檔案整理在時間流裡很彆扭 —— B 的解法

### 4.1 先承認問題

整理檔案是**空間性**的工作：你要同時看到來源與目的地、要多選、要比較兩棵樹的形狀。時間序對這件事毫無幫助——把資料夾樹塞進時間流會變成「每天都重畫一次同一棵樹」。

迴避這個問題的做法（例如把硬碟做成第六個分頁）會讓提案退化成 A。B 選擇**正面切開**。

### 4.2 三層解法

**(a) 時間流只顯示檔案事件，不顯示檔案樹。**
流上的檔案事件只有三種語句：
- 「客戶交了 6 份文案進收件匣」
- 「整理了 4 個檔案 → 修改需求/」
- 「Sitemap.docx 改成對客戶可見」

每一則展開後列出逐檔（檔名、kind、大小、可見性），但**沒有樹**。理由：這三句話是「發生了什麼」，而樹是「現在長什麼樣」——後者不屬於時間軸。

**(b) 側抽屜裡是完整的多層樹。**
瀏覽、展開收合、看每一層的可見性與檔案數，全部在硬碟抽屜裡做。樹的節點名稱直接用 Owner 現場的名字（`[共用] 官網專案＿共好玟化 X 圓展`、`專案啟動［正式資料］`、`20260411_M04_網站資源一版`…），系統不另設 `01_Docs / 02_Assets`。

**(c) 整理模式：時間流讓位。**
點收件匣 chip 或抽屜底部的「整理收件匣（N）」，**時間流整個收起來**，換成一個全幅的兩欄整理台：

```
左：收件匣（role='inbox' 的真資料夾）    右：移到哪裡（縮排的資料夾樹）
    ☑ 共好玟化_第二版範圍草案.pdf            [共用] 官網專案＿共好玟化 X 圓展  對客戶可見
    ☑ LINE_分期對話截圖.PNG                    └ 01.確認文案…                  對客戶可見
    ☐ 二期估價_草稿.xlsx                       └ 修改需求                       對客戶可見
                                            專案啟動［正式資料］              僅內部
    [ 移動 2 個檔案 ]  [ ← 回到時間流 ]      只改 folderId，不動 R2 bytes
```

整理完成後，流上留下**一則**「整理了 2 個檔案 → [共用]…/修改需求」。

### 4.3 為什麼這個解法站得住

1. **它誠實。** 不假裝整理是時序的。給空間性的工作一個空間性的版面，是比硬塞更尊重工作本身的做法。
2. **它與資料模型對齊。** `DESIGN §4.5` 已經定了收件匣是 `kind=INBOX` 的真資料夾 ＋ `filedAt`。整理模式就是 `moveProjectAssets({ assetIds, toFolderId })` 這一個服務的 UI；「待整理 N」＝ `count(folderId = inboxId)`。
3. **它讓時間流更乾淨。** 一次整理 20 個檔案在流上只有一則，而不是 20 則。
4. **代價可控。** 整理模式是一個獨立的檢視狀態（`S.tidy`），不污染時間流的渲染邏輯；它和 C 提案的雙欄樹**不是同一個東西**——C 把樹當成常駐主幹，B 把它當成一個進得去、出得來的模式。

### 4.4 不做的事

- 不做拖放（P2）。整理模式用勾選 ＋ 選目的地 ＋ 一個按鈕，鍵盤與觸控都能用。
- 不做自動分類。`MIG §2` 已經決定「原始結構原樣保留、重整是第二步、由使用者按」。

### 原型可以真的點的流程

- 切換 5 個專案（各自不同的時間流、期、樹、計劃）

## 7. 取捨與風險

### 7.1 B 得到什麼

| 收穫 | 說明 |
|---|---|
| 與既有心智模型一致 | 日誌／回顧／今日脈絡／物件索引時間軸已經把 Owner 訓練好了。專案時間流不需要教學 |
| 「這個案子發生了什麼」一眼可讀 | 分頁式介面沒有任何一頁能回答這個問題 |
| 新事件天然匯流 | 新訊息、新會議、新檔案進收件匣、里程碑到期、報價到期，全部匯成同一條河，不需要使用者去五個地方巡一遍 |
| 「期」是結構紅利 | 二期在流上是一條看得見日期的線，不是一個欄位值 |
| 誠實面對缺口 | 外部缺口（LINE 上的口頭約定）可以當成**一則事件**放在流上，這在分頁式介面裡沒有自然的家 |

### 7.2 B 付出什麼

| 代價 | 嚴重度 | 緩解 |
|---|---|---|
| **檔案整理需要離開時間流** | 中 | §4 的整理模式。承認它是另一個模式，而不是假裝流能做 |
| **「現在的狀態」要自己讀出來** | 中 | 時間流擅長「發生了什麼」，不擅長「現在長什麼樣」（例如：現在總共有幾個檔案、哪些任務未完成）。緩解：頁首的期尺 ＋ 資源 chip 上的計數就是常駐的狀態摘要；深度狀態在抽屜裡 |
| **長專案的流會很長** | 中 | 期篩選 ＋ 類型篩選 ＋ 期尺跳轉。`01` 七個月 16 則還可讀；兩年期的專案需要再加「摺疊整個階段」與虛擬捲動 |
| **聊天密度判斷可能錯** | 中 | 折疊規則是一天一則。若某案一天 200 則，摘要那一行要顯示更多線索（誰說的、幾個未讀、是否有附件）。這是上線後要觀察的第一個數字 |
| **抽屜是 overlay，看不到流** | 低 | 刻意的。寬螢幕可以之後改成推開式（`grid-template-columns` 多一欄），但 1440 以下必須是 overlay |
| **與 v5 其他模組的版面語言有落差** | 低 | B 的卡片、標籤、樹、表格全部沿用 v5 元件；落差只在「單欄流」這個骨架，而日誌的回顧分頁已經是單欄流了 |

### 7.3 風險

1. **入流規則是產品判斷，不是技術選擇。** 這十類進／五類不進如果定錯，流會變成雜訊或變成空的。建議上線後保留一個「顯示全部操作」的 debug 切換，拿兩週的真實資料回頭校正。
2. **時間流不能取代狀態頁。** 如果 Owner 的高頻問題其實是「這個案子現在有哪些事沒做完」，B 的主幹答不好這題——那應該選 A 或 C。這是 Owner 批准時要先確認的。
3. **補記（`at ≠ d`）在專案尺度上比日誌更常見。** 匯入 `0_工作區` 時，202 個檔的 `occurred_at` 全部是 2026-10 的匯入時刻，而 `on_date` 是檔案 mtime —— 照 `journal-timeline-backdating-decision.md` 的規則，它們會**全部落進補記區**。必須在匯入器裡把 `occurredAt` 設成 mtime 而不是 now()，否則第一天打開專案頁會看到一條空的時間流 ＋ 一個 202 筆的補記區。**這是 B 特有的、必須在 P1-A 遷移前處理的坑。**
4. **`NN.` 編號會回收**（`09` 用過兩次），所以時間流的事件不能用資料夾編號當外鍵；用 `PRJ-{YYYY}-{SEQ}`，`legacyFolderNo` 另存並併進 `mentionHits()` 的搜尋來源。

## 8. 實作成本評估

### 8.1 機制前提

- v5 的 runtime 是 `*.source.js` ＋ `source-patches.mjs` 由 `scripts/generate-yuanzhan-v5.mjs` 組出 `runtime.js` ／ `styles.ts` ／ `v5-seed.js`。**改 source 後必跑 `npm run ui:yuanzhan:v5:generate`。**

### 8.4 B 特有的額外成本（相對 A）

1. **入流規則引擎**（約 200–300 行）：把 10 類事件從各自的集合彙總成一條流，並做折疊（檔案一批一則、對話一天一則）。A 不需要這個。
2. **匯入時的 `occurredAt` 處理**（見 §7.3 第 3 點）：否則第一天的時間流是空的。
3. **期分隔器的推導**：便宜（由 `event.cyc` 變化推導），但要有 `ProjectPhaseCycle` 這張表 —— 這是 `RES-033 §4` 已經規劃的 Migration ②，三案共用。

### 8.5 不在本提案範圍

LINE 導入、`0_工作區` 真實檔案遷移、`FileAsset`/`MediaAsset` 收斂、`OperatingThread` 收斂、全文搜尋、音訊轉錄、拖放搬移、虛擬捲動。
