## 0. 一句話

**五大資源不增加分頁總數。** 現況六分頁（總覽／工作／對話／Evidence Repo／財務／里程碑）→ 重組後仍是六分頁，深度全部推進 v5 既有的「分頁內子視圖」慣例（`工作` 的 清單／看板／表格／日曆、`金流` 的 收單／帳務／洞察 已經是這個形狀）。

刻意的取捨：分頁天生切斷資源之間的關聯。A 用**四個就地機制**把關聯補回來，而不是再開一個「關聯」分頁 —— 那只會證明批評是對的。

## 3. 「期」怎麼表達（約束 2）

### 在計劃分頁
分頁列正下方一條 **期列**（`.cyc-bar`）：`期1 一期 完成 › 期2 二期（第二次修改）進行中 › ＋新增期`。選中某一期後，下方展開那一期自己的**階段軌**：

```
期1 一期          提案 › 接案 › 執行 › 驗收
期2 二期（第二次修改）  追加合約 › 執行 › 驗收
```

`執行→驗收` 因此在兩期各出現一次，而不是被壓成一個平面 enum 的兩個值。同一期內 `執行→驗收→執行→驗收` 也畫得出來（`stageKind` 不唯一，階段軌會顯示 `×2`）。

### 在總覽分頁
同一份資料用兩列階梯呈現，一眼看完整條生命週期，不必進計劃分頁。

### 在檔案分頁
`修改需求／第二次修改需求` 資料夾帶 `二期入口` 標籤 —— 期不只是計劃分頁的概念，它在硬碟裡本來就有實體對應（Owner 的既有慣例）。

### 模型
- 「期」是一列 `ProjectPhaseCycle`（`projectId`/`ordinal`/`title`/`contractId?`/`budgetAmount?`/`startOn?`/`endOn?`）。
- **加三期不需要 migration、不需要改 enum**：插一列 ＋ 一次 UPDATE 把「結案」移過去。原型的「新增期」流程就是在示範這件事。
- 「現在走到哪」**推導不存**：最小未完成的 `(cycle.ordinal, stage.ordinal)`。
- `phaseCycleId` 必須可空，否則 v5 既有的 `phases` 寫入當場壞掉（PLN-075「不可觸碰」）。

## 4. 關聯問題的解法（A 的主要設計負擔）

分頁架構最難表達的就是「會議產出→任務」「聊天訊息→任務」「檔案→里程碑」。A 的立場：**不要用導航解決關聯，用就地可見性解決關聯。** 四個機制：

### M1 引用晶片（ref chip）
任何物件都把它的跨資源連結渲染成虛線小晶片：`→ M05`、`→ 會議 0919`、`→ 對話 09-22`。晶片在里程碑列、任務列、檔案列、訊息列、關鍵時間列都一樣長，是一套元件不是五套。

### M2 懸停卡（hover peek）——最重要的一個
滑過引用晶片即浮出目標物件的本體：里程碑顯示期／日期／驗收／任務數；**會議直接顯示四個屬性**；檔案顯示位置／大小／可見性。

> 這是 A 對「分頁切斷關聯」最實質的回答：**多數關聯確認變成一次 hover，而不是一次導航。** 導航次數下降，分頁的代價就下降。

### M3 回返脈絡列（return context bar）
點晶片真的跳過去時，目的分頁頂端出現一條脈絡列：「從 **會議 · 2026-09-19 第二次修改需求對焦** 跳來 · ← 返回來處」。採堆疊，支援多跳（顯示「共 n 層」），`Esc` 逐層退回。**跨分頁跳轉永遠不會把人丟在陌生的地方。**

### M4 就地升級抽屜（三條升級路徑）
`訊息→任務`、`會議待辦→任務`、`結論→決議` 一律用**側抽屜蓋在當前分頁上**，不切換分頁。建立時**雙向寫入引用**：任務列出現「對話 09-22」，訊息列出現任務代號並標「已升級」。原型中這兩條路徑都可以真的走完。

### M5 總覽的跨資源待辦
分頁架構還是會有「東西散在各處、不知道哪裡有洞」的風險。總覽把四類跨資源缺口一次攤開（收件匣待整理／會議結論未寫／訊息可升級／里程碑日期待補），每一列都是 M3 的跳轉。這是**清單，不是分頁** —— 它不新增一個操作面，只是把既有分頁的缺口集合起來。

## 6. 取捨與風險

### 最大的取捨
**為了守住六分頁，必須刪掉兩個 Owner 已經熟悉的分頁位置（工作、Evidence Repo）。** A 的主張是「學習成本最低」，但這一刀本身就是學習成本 —— 兩者有張力。緩解：兩者都降級為**子視圖**而非消失，位置可預測（工作在計劃裡、Evidence Repo 在檔案裡），且子視圖的段控是 v5 既有慣例。

### 風險

| 風險 | 說明 | 緩解 |
|---|---|---|
| **R1 分頁上限** | 六分頁已接近寬度極限（1440 下約 420px）。再加任何一個頂層分頁就要水平捲動，A 的主張失守 | 寫成硬規則：**五大資源之後不再新增頂層分頁**，一律進子視圖 |
| **R2 子視圖深度** | 檔案分頁已有 3 個子視圖；若 Evidence Repo 之後要版本演化、結案檢查、待歸檔三組，子視圖可能再分層 → 三層導航 | 子視圖上限設 4；超過就回頭檢討分頁切法 |
| **R3 關聯仍是次等公民** | M1–M5 讓關聯可見，但「這個檔案被哪三個里程碑引用」仍只能從檔案那一側看；沒有雙向關聯的全域視圖 | 接受。全域關聯視圖是提案 C 的強項，A 刻意不做 |
| **R4 會議分頁與檔案分頁重疊** | 一場會議既在會議分頁，也在檔案樹的 `會議/` 底下 —— 兩個入口看同一個資料夾 | 以「在硬碟開啟 →」按鈕明示兩者是同一個東西，不是兩份資料；會議分頁不提供檔案 CRUD，只讀 |
| **R5 多層資料夾在單欄裡吃緊** | 樹深 5 層時左欄 260–330px 會不夠 | 樹列縮排 13px／層、面包屑補位；真要更深則需橫向捲動（C 在這點優於 A） |
| **R6 跨分頁跳轉的回返堆疊** | 多跳後堆疊深度可能讓人迷路 | 脈絡列顯示層數、`Esc` 逐層退、切換頂層分頁即清空堆疊 |

## 7. 實作成本評估

### 7.1 關鍵機制前提
v5 runtime 由**凍結的 Owner 原型 HTML** ＋ `source-patches.mjs`（窄幅 `rep(old,new)`）＋ 19 支 `*.source.js` 擴充檔，經 `node scripts/generate-yuanzhan-v5.mjs` 組成 `runtime.js`。`runtime.js` 與 `styles.ts` **永不手改**。寫入一律走 `commit()`（`ARC-042`），不開 Server Action 旁路。

**對 A 特別有利的一項實測發現**：專案分頁陣列雖然定義在凍結原型（`runtime.js:676` `tabs: ['總覽','工作','對話','Evidence Repo','財務']`），但 `operating-converge.source.js:257` 已經在用
```js
if (proj && !proj.tabs.includes('里程碑')) proj.tabs = [...proj.tabs, '里程碑'];
```
從**團隊自有的擴充檔**改寫它。所以 **A 的分頁重組完全不需要動 `source-patches.mjs`** —— 直接在擴充檔裡覆寫 `WB.find(w=>w.id==='project').tabs` 與 `VIEWS.project` 即可。這是 A 相對 B／C 最實在的成本優勢。
