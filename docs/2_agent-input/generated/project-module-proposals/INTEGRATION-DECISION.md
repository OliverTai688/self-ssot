## 1. 決策一句話

**以 A 的分頁外殼為容器，把 C 的資源樹放進「檔案」與「會議」兩個分頁內，把 B 的時間流放進「總覽」當主欄。**

這不是「三案都要」。三案各自回答了**不同層級的問題**，而它們的強項沒有重疊：

| 問題層級 | 誰回答得最好 | 為什麼 |
|---|---|---|
| 專案模組怎麼坐進 v5？ | **A** | 工程證據決定（見 §2） |
| 多層資料夾 CRUD 與會議資料夾怎麼做？（需求②⑤） | **C** | `parentId` 樹＋右欄是唯一真正成立的形狀 |
| 「這個案子到今天為止發生了什麼」怎麼讀？ | **B** | 時間流是唯一能把 LINE 斷點、二期切分講成一個故事的形狀 |

## 2. 為什麼外殼用 A：工程證據，不是品味

實測 `src/components/yuanzhan/v5/operating-converge.source.js:254-266`：

```js
/* ---------- 專案模組：加分頁 + 總覽加目標對齊 ---------- */
if (opConverged()) {
  const proj = WB.find(w => w.id === 'project');
  if (proj && !proj.tabs.includes('里程碑')) proj.tabs = [...proj.tabs, '里程碑'];
}
const opPrevProject = VIEWS.project;
VIEWS.project = tab => { ... };
```

團隊**已經**用「擴充檔覆寫 `VIEWS.project` ＋ 改 `proj.tabs` 陣列」的慣例加過分頁。這條路不需要碰 `source-patches.mjs`。

對照：`source-patches.mjs` 有 **45 個 `rep()` 呼叫**，每一個都是「找不到原文就 `throw Error('v5 patch no longer matches: ...')`」。它是整個 v5 最脆弱的地方。

→ **A 的外殼是唯一一個完全不增加 `source-patches.mjs` 風險的方案。** B 與 C 若當外殼，都要改動專案模組的版面骨架，而骨架改動最容易讓既有 patch 失配。這是決定性的理由，優先於任何視覺偏好。

## 3. 為什麼樹用 C，但只在兩個分頁內

C 的樹是三案裡唯一真正解決需求②與⑤的形狀：`parentId` 遞迴樹、收件匣是樹上的真資料夾、資料夾被選取時右欄同時顯示會議四屬性與夾內材料。A 的「檔案」分頁本來就需要一個這樣的東西，C 已經把它做好了。

但 C **不當外殼**，理由有二，其中一條是我自己實測的：
1. **實測 390px 橫向溢出**（`document.documentElement.scrollWidth > innerWidth`）。A 與 B 皆為 `false`，C 為 `true` → 違反 PLN-075 的版面約束。C 自己的報告也承認「手機上側欄幾乎不可用」。
2. 它會是 v5 唯一有常駐側欄的畫面。C 提出的三道緩解（只在一個分頁內生效、`⌘B` 收起、沿用 token）其實正好說明：**把樹收進分頁內，是 C 自己也認同的終點。**

→ 採用 C 的樹，放進「檔案」與「會議」分頁；放棄 C 的模組級常駐側欄。窄螢幕左欄自動收成抽屜，且必須修掉溢出。

## 4. 為什麼時間流用 B，但只在總覽

B 的時間流是唯一能把這些講成一個故事的形狀：二期從 `2026-09-19 第二次修改需求書` 那天切開；`01` 的「合約變更只存在 LINE 裡」成為時間軸上一個明確的**外部缺口事件**。這對 Owner 的「追蹤節奏」訴求有真實價值。

但 B **不當主幹**，理由是 B 自己的誠實承認：

> 時間流擅長「發生了什麼」，不擅長「現在長什麼樣」。若 Owner 的高頻問題其實是「這案現在有哪些事沒做完」，B 的主幹答不好這題。

Owner 的原話是「追蹤節奏」與「確保細節任務」——那是**現在狀態**的問題。而 A 的總覽已經有「跨資源待辦」在答這題。

→ 總覽＝上半 A 的期階梯＋跨資源待辦（現在長什麼樣）／下半 B 的時間流（發生了什麼）。兩者互補，不衝突。

## 5. 整合後的分頁與落點

沿用 A 的六分頁（總數不變，不新增抽屜櫃）：

| 分頁 | 內容 | 來源 |
|---|---|---|
| **總覽** | 期階梯（期1/期2，`執行→驗收` 各出現一次）＋跨資源待辦＋五資源入口 ／ 下半為時間流 | A ＋ B |
| **計劃** | `期 → 階段 → 里程碑 → 任務` 四層；TODO 與**審核任務**（審核人／結果／退回） | A（C 的規劃版面併入） |
| **檔案** | C 的資源樹；收件匣為 `role='inbox'` 真資料夾；整理＝只改 `folderId`，不動 R2 bytes | **C** |
| **會議** | 時間序清單 ＋ C 的會議資料夾視圖（四屬性＋四件套完整度） | A 的時序 ＋ C 的屬性框 |
| **對話** | 一列一訊息；附件走與其他入口相同路徑落進收件匣（`origin='chat'`、`filedAt=null`） | A ＋ C 的落點設計 |
| **財務** | 現況不動 | 既有 |

### 採納的跨案細節
- A 的**懸停卡**作為關聯主解（多數確認變成 hover 而非導航）、**回返脈絡列**（跨分頁跳轉可堆疊、Esc 退回）、**引用晶片**。
- C 的 `ProjectFolderKind` **enum 而非字串 role**（讓「哪些 kind 禁 client_visible」在 schema 層就看得見）。
- C 的**三級可見性**：客戶可見／內部禁對客戶／**最高敏感不建索引**。第三級是 `05/商城專案資訊.docx` 明文密碼所必需——資料夾權限擋不住全文索引。
- C 的 `ProjectMilestone.folderId?`：`20260411_M04_網站資源一版/` 成為 M04 交付夾，**是連結不是包含**，資料夾不被搬走。
- B 的**入流規則**（一則＝一個對外看得見的事；單則聊天訊息不進流；對話一天折疊成一則）。
- B 的**匯入陷阱**：匯入 `0_工作區` 時 `occurredAt` 必須取檔案 mtime，否則 202 個檔全落進補記區、主時間流是空的。

### 明確放棄
- C 的模組級常駐側欄（改為分頁內、可收起）。
- B 當主幹、B 的全幅「整理模式」（與「檔案」分頁重複，改為檔案分頁的批次選取）。
- A 刪掉「工作」與「Evidence Repo」兩個分頁位置的做法——**改為保留它們為「計劃」與「檔案」分頁內的子視圖入口**，避免 Owner 既有肌肉記憶落空。
