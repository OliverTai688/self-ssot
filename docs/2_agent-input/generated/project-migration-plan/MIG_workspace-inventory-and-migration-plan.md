### 2.2 R2 key 命名策略

沿用既有慣例並只加一段 scope：

```
operating/{workspaceId}/project/{projectId}/{yyyy-mm}/{uuid}{ext}
```

**關鍵決定：object key 裡不放資料夾路徑、不放原始檔名。** 三個理由，每個都是實際會痛的：

1. **R2（S3 API）沒有 server-side rename。** 如果 key 編了路徑，使用者在雲端硬碟裡把 `提案/` 改名成 `提案與訪談/`，就得把底下每個 object 複製一份再刪舊的——對 202 個檔沒事，對一年後的 2 萬個檔就是一筆算不清的 Class A 費用與一個會中斷的作業。
2. **中文／全形字元在 key 裡是編碼地雷。** `附件G：跨域研發聯盟合作協議書參考範本 (含義務釐清事項).doc` 這種名字要經過 presign 簽章、HTTP header、不同 SDK 的 URL encoding 三道關；一個環節 normalize 方式不同（NFC vs NFD，macOS 檔名預設 NFD）簽章就對不上，而且**錯誤訊息會是 403 SignatureDoesNotMatch，完全看不出是檔名問題**。
3. 既有 `OperatingAsset.objectKey` 已經是 `{uuid}{ext}` 的 opaque 形式，不該為專案硬碟破例。

**顯示名稱、資料夾位置、原始路徑全部存 DB**：`displayName`（可改，不影響 refCode）＋ 新的 `folderId` ＋ 新的 `importSourcePath`（原始相對路徑，原樣保留，是日後對帳與「我當初放在哪」的唯一依據）。

`{yyyy-mm}` 用**原始檔案的 mtime 月份**而非匯入月份——否則 202 個檔全部落在 `2026-10`，日後按時間瀏覽 bucket 等於沒分。

### 2.3 新資料模型：資料夾樹與收件匣

```prisma

  workspaceId String  @map("workspace_id") @db.Uuid

  sortKey     Int     @default(0) @map("sort_key")
  /// proposal | contract | meeting | milestone | material | shared | internal | revision | finance | inbox | custom
  /// 建立時由範本指定，讓「合約」這類資料夾能被規則認得（例如禁止 CLIENT_VISIBLE）
  role        String  @default("custom")
  visibility  String  @default("internal")   // internal | client_visible
  /// 一場會議＝一個資料夾時，掛在這裡（Occasion 已有 actorIds / recap / prep）
  occasionId  String? @map("occasion_id") @db.Uuid
  deletedAt   DateTime? @map("deleted_at")
  @@unique([projectId, parentId, name], map: "drive_folders_sibling_name_unique")
  @@index([workspaceId, projectId])
}
```

`OperatingAsset` 加三欄（都可為 null，不破壞既有日誌上傳）：`folderId`、`projectId`、`importSourcePath`、`importBatchId`。

**收件匣不是一個新表**，是 `role = 'inbox'` 的那個資料夾：上傳沒指定位置就落在那裡，整理就是改 `folderId`。這比開第二張表好，因為「收件匣裡的檔案」和「已整理的檔案」在 `@` 引用、搜尋、下載授權上行為必須完全一樣——分兩張表就要寫兩套。

### 2.4 哪些上雲、哪些不上

| 類別 | 處置 | 理由 |
|---|---|---|
| 202 個檔中的 201 個 | **上雲** | |
| `.DS_Store`（1 個） | **排除** | macOS 索引檔，零價值 |
| 6 組重複檔（12 個檔，省約 580 KB） | **全部上雲，但建立引用關係** | 不要在匯入時自動去重。`[共用]/01.確認文案/` 與 `M04_網站資源一版/` 兩份是**不同語意**（對外共用 vs 里程碑快照），刪掉任一份都會讓「M04 當時交付了什麼」查不到。以 `contentHash`（finalize 時由 HeadObject ETag 寫入，欄位已存在）標示「與另 n 個檔內容相同」即可 |
| `.odt` / `.odp` / `.doc`（10 個，SBIR 官方範本） | **上雲，白名單必須放寬** | 官方範本的同一性不能用另存取代 |
| `.svg`（4 個 logo） | **上雲，但只允許匯入路徑、且強制 `Content-Disposition: attachment`** | `EXPLICIT_DENY` 的理由（SVG 可內嵌腳本）在**使用者上傳**情境成立，但這 4 個是客戶品牌向量原稿、來源可信、是 Owner 自己的既有檔案。折衷：匯入器可帶，互動上傳維持拒絕 |
| 負責人身分證正反面、稅籍公文、公司登記表 | **上雲但列敏感**（見 §4.5） | 這是金流申請的必要文件，不上雲等於這個專案進不了系統 |
| `05. 金流商城申請 - 5/商城專案資訊.docx` | **先不上雲，請 Owner 處理後再匯入** | 見 §4.5。這份檔案裡有明文密碼 |

### 2.5 保留 vs 重整原始結構

**兩者都做，分兩層。**

- **原始結構原樣保留**：每個檔的 `importSourcePath` 存完整相對路徑，資料夾樹第一版就是 `0_工作區` 現有的樹（逐層照建，含 `[共用] 官網專案＿共好玟化 X 圓展` 這種名字）。理由：**搬遷當天不能同時改變結構，否則對帳對不起來、使用者也找不到東西**。檔案數／位元組／路徑三者都能一比一比對。
- **重整是第二步、在系統裡做、由使用者按**：匯入後提供一個「套用標準資料夾樹」動作，把現有資料夾對應到 §1.5 的 role（`開案前`→`提案`、`專案啟動［正式資料］`→`里程碑交付`、`[共用] …`→`共用（對客戶）`…），使用者確認後才搬。因為 R2 key 不含路徑，這一步**只改 DB 的 `folderId`，不動一個 byte**——這正是 §2.2 那個決定換來的好處。

### 2.6 檔名正規化

**原則：原始檔名一個字都不改，正規化只發生在「衍生值」上。**

| 欄位 | 處理 |
|---|---|
| `displayName` | 原樣（含全形、空白、中文）。使用者看到的就是他本來的檔名 |
| `importSourcePath` | 原樣，但**統一 Unicode NFC**。macOS 檔名是 NFD（`ㄅ`＋組合符號分開存），同一個「霽」在 NFD 與 NFC 下位元不同，日後用路徑比對會莫名對不上 |
| `objectKey` | 不含檔名，只留 `{uuid}{ext}`，`ext` 轉小寫（實測有 9 個 `.PNG` 大寫副檔名，`EXTENSION_KINDS` 的 key 全小寫，不轉就會被判定不在白名單） |
| 下載時的檔名 | `Content-Disposition` 用 RFC 5987 `filename*=UTF-8''<percent-encoded>`，不要用 `filename=`（非 ASCII 會被某些瀏覽器截成亂碼） |
| 搜尋索引 | NFC ＋ 全形轉半形 ＋ 去空白後的副本，存在 `extractedText` 旁或獨立欄位。否則使用者打半形 `(` 搜不到檔名寫全形 `（` 的檔 |

### 2.7 上傳批次與驗證（對帳）

一次匯入＝一個 `importBatchId`。**對帳四條，缺一條就不算搬完**：

1. **數量**：`SELECT count(*) FROM operating_assets WHERE import_batch_id = ? AND status='ready'` ＝ 來源檔案數 − 排除數（202 − 1 ＝ **201**）。
2. **位元組**：`SUM(size_bytes)` ＝ 437,680,944 − 6,148（`.DS_Store`）＝ **437,674,796**。
3. **內容**：匯入器在本機先算每個檔的 md5，finalize 後與 R2 HeadObject 的 ETag 比對（單次 PUT 的 ETag 就是 md5；multipart 不是，要改比 SHA256 checksum header）。不符的檔標 `failed` 並列進報告，**不自動重試**——重試會掩蓋「檔案在搬遷途中被改」這件事。
4. **抽樣開檔**：每個專案抽 2 個檔（1 個最大、1 個隨機）實際用下載網址開起來看。自動化驗不了「docx 打開是不是亂碼」。

對帳報告寫成一份檔（`import-batch-{id}-reconciliation.md`），列出：每專案的檔案數／位元組對照、所有 `failed`、所有被排除的檔與理由、重複組清單。**沒有這份報告就不要刪本機原檔。**

### 2.8 上傳工具形式

**兩個都要，但順序是先 script 再介面。**

**第一階段：一次性 Node script**（`scripts/import-workspace-folder.ts`）
- 吃一個本機資料夾路徑 ＋ `--dry-run` ＋ `--project-map <csv>`。
- 先跑 `--dry-run`：輸出計畫（會建幾個資料夾、幾個檔、哪些被拒、哪些超門檻），不動任何東西。
- 走**伺服器端憑證直接 PutObject**，不走預簽網址。理由：預簽是為「瀏覽器不該拿到憑證」設計的，一次性本機搬遷沒有這個需求，而且 900 秒 TTL 對 76 MiB 的檔在家用上傳頻寬下**真的會過期**。
- 不可重入會毀掉一切，所以**設計成可重跑**：以 `(importBatchId, importSourcePath)` 為幂等鍵，已 `ready` 的跳過。

為什麼不先做介面：202 個檔、15 個專案、一次性。做一個 wizard UI 要處理拖整個資料夾、瀏覽器記憶體、斷線續傳；script 一個下午就能跑完並對帳。

**第二階段：系統內的匯入介面**（持續用）
- 專案雲端硬碟的「上傳到收件匣」（拖放／手機拍照），走既有預簽路徑。
- 「從資料夾建立專案」wizard（§3.3），因為**日後還會有新專案是從資料夾開始的**——`10`/`11`/`12` 都是最近三個月才開的資料夾，這個習慣不會因為上了系統就消失。

### 2.9 權限與分享

- **Bucket 維持 private**（`RES-022 §3`：public bucket 是全有全無）。所有下載都是即時簽發的短 TTL 網址，永不落地。
- 既有的 `uploads/route.ts` 已經做對一件關鍵事：**workspaceId 由伺服器從 session 解析，不吃前端參數**。新的專案維度授權必須照抄這個形狀——`projectId` 也不能由呼叫端決定可見範圍，要反查 `ProjectAccessGrant`。
- **資料夾 `visibility` 是授權的來源，不是標籤。** `role='shared'` 的資料夾＝ `CLIENT_VISIBLE`，其餘預設 `internal`。`role='contract'` 與 `role='internal'` **禁止**被設為 client_visible（`06` 的「內部文件｜不得提供客戶」就是這個規則的現場版本）。
- **對客戶分享用 `Project.clientToken`（欄位已存在）＋ 只讀視圖**，不要直接把 R2 預簽網址貼給客戶：網址一旦外流就無法撤銷，而 token 可以。
- 音訊播放的 TTL 坑（提案 D3）在這裡會真的踩到：兩段股東會議錄音各 40 分鐘以上，`<audio>` 靠 HTTP Range 續讀，5 分鐘 TTL 到期後 403，播放器只顯示「無法播放」。**建議下載 TTL 對 audio/video 延長到 1 小時**，或播放器自動換網址。

## 第三部分　Q2：專案初始化介面與自動建在園展教育科技有限公司底下

### 3.1 必須先知道的四個既有事實（否則設計會踩空）

**事實一：系統裡沒有 Company 或 Client 模型。** 全 schema 搜不到 `model Company` / `model Client` / `model Contact`。公司＝ `Workspace`（`type: TEAM`、`slug` 唯一），客戶＝ `Project.clientName`（**自由文字**）＋ `OperatingProjectProfile.client`（也是自由文字）。
→ 所以「在園展教育科技有限公司底下建立專案」在資料層的意思是：**`Project.workspaceId` 指向 slug 為 `yzedtech` 的那個 Workspace**。`OPERATING_WORKSPACE_SLUG = DEFAULT_ORG_KEY = "yzedtech"`（`src/lib/services/operating-settings.service.ts:18`）。

**事實二：現行的 `createProject` 根本不會設 workspaceId。** 這是 Q2 最硬的一個阻斷點：

```ts
// src/lib/services/project.service.ts:98
export async function createProjectForProfile(profileId, input) {
  return await db.project.create({ data: {
    ownerId: profileId, name, clientName, description,
    status, phase, health, visibility, dueAt,
  }})                       // ← 沒有 workspaceId
}
```
`Project.workspaceId` 是 optional，`accessMode` 預設 `PRIVATE`。**所以今天從 `/work` 的「新增專案」建出來的每一個專案都是 workspaceId = null 的私人專案，不屬於園展，`projects_workspace_status_idx` 查不到，營運工作台也看不到。** 這不是設計選擇而是缺口——`createProject` 必須加上 workspace 解析，否則「自動建在公司底下」做不到。

**事實三：AI 專案初始化的介面殼已經存在，但解析是假的。**
`src/components/work/project/add-project-dialog.tsx` 已有 `manual` / `ai` 兩個 mode，AI mode 有 `upload → parsing → preview` 三步、會把上傳檔真的 PUT 進 R2（`requestFileUpload`）。但它呼叫的 `src/lib/ai/project-init.ts` 第 23 行自己寫著 `// Phase 1 mock — simulates AI document parsing with a realistic delay`：**回傳的是 `setTimeout(2200)` 之後的一組寫死的四階段里程碑，跟上傳的檔案完全無關**。
→ 好消息：UI 不用重做。要做的是把 mock 換成真解析，並把單一專案擴成批次。

**事實四：三套階段詞彙並存，而且沒有一套是使用者說的那五階段。**

| 來源 | 詞彙 |
|---|---|
| `ProjectStatus` | `EXPLORING / ACTIVE / PAUSED / COMPLETED / ARCHIVED` |
| `ProjectPhase` | `DISCOVERY / PLANNING / EXECUTION / REVIEW / MAINTENANCE` |
| `ProjectDealStage` | `CHALLENGEABLE / PROPOSED / WON / CLOSED` |
| `OperatingProjectProfile.operatingStatus`（自由字串） | `商機 / 進行中 / 驗收中` |
| **使用者要的** | **提案 → 接案（合約）→ 執行（里程碑）→ 驗收 → 結案**，且 執行→驗收 可重複 |

**建議：新增單一權威欄位，其餘全部由它推導。**

```prisma
enum ProjectLifecycleStage { PROPOSING  CONTRACTED  EXECUTING  ACCEPTANCE  CLOSED }

model OperatingProjectProfile {
  // ... 既有欄位
  lifecycleStage  ProjectLifecycleStage @default(PROPOSING) @map("lifecycle_stage")
  /// 第幾期。執行→驗收 回圈時 +1；一期＝1。沒有它，「二期」就只能靠改專案名稱表達
  phaseRound      Int @default(1) @map("phase_round")
  /// 使用者資料夾的 `- N` 後綴。語意待 Owner 定義，先原樣保存不解讀

  /// 原始資料夾序號（`00`–`12`）。會被回收，所以不是唯一鍵
  legacyFolderNo  String? @map("legacy_folder_no")
  importSourcePath String? @map("import_source_path")
}
```

映射表（寫成一支純函式 `deriveProjectStatus(lifecycleStage)`，單一 writer）：

| lifecycleStage | ProjectStatus | ProjectPhase | ProjectDealStage | operatingStatus |
|---|---|---|---|---|
| PROPOSING | EXPLORING | DISCOVERY | PROPOSED | 商機 |
| CONTRACTED | ACTIVE | PLANNING | WON | 進行中 |
| EXECUTING | ACTIVE | EXECUTION | WON | 進行中 |
| ACCEPTANCE | ACTIVE | REVIEW | WON | 驗收中 |
| CLOSED | COMPLETED | MAINTENANCE | CLOSED | 已結案 |

**為什麼不直接改 `ProjectDealStage`**：獎金閘門③會讀 `operatingStatus`（schema 註解明寫），金流推演讀 `dealStage`。動它們等於同時動金流。加一層權威欄位＋推導函式，既有讀取端一行都不用改。

### 3.3 批次匯入既有專案的 wizard（從資料夾建立專案）

四步，**每一步都要能退回上一步，第三步之前不寫任何資料**：

**① 掃描** —— 選本機資料夾（或 §2.8 的 script 產出的 JSON）→ 列出頂層資料夾、每個的檔案數／位元組／mtime 範圍／偵測到的子資料夾 role。

**② 對應** —— 一列一個候選專案的可編輯表格：

| 來源資料夾 | 要建成專案？ | 專案名稱 | 客戶 | 範本 | lifecycleStage | priorityTier | 備註 |
|---|---|---|---|---|---|---|---|

系統預填（下方 §3.5 那張表就是預填值），使用者逐列改。三個特別情況介面必須處理：
- **不是專案**：`20260818股東會議` → 轉成 `Occasion`；`研究發表線` → 轉成研究線/公司層文件。選項要有「不建成專案」。
- **一個資料夾裡其實有兩件事**：`05. 金流商城申請` 含「圓展自己的商城申請」與「新屋愛鄉協會資料區」兩個不同主體；`08. 大考中心` 含提案與一個不相關的「宣傳影片-歐洲故事箱紙偶劇場版本」。介面要能**拆成兩個專案**（一列變兩列，各自挑子資料夾）。
- **封存**：`封存的專案/` 底下三個要建成 `lifecycleStage: CLOSED` ＋ `ProjectStatus: ARCHIVED`，而不是跳過。歷史提案是日後報價的參考資料。

**③ 預覽** —— 不寫 DB，只算：會建 n 個專案、m 個資料夾、k 個檔（含 j 個被白名單拒、1 個超 multipart 門檻）、總位元組、每個專案第一組里程碑長什麼樣、refCode 會長什麼樣。**這一頁要能匯出成檔**（它就是對帳基準）。

**④ 確認** —— 一個 transaction 建專案與資料夾樹（快、可 rollback），檔案 bytes 另外非同步批次傳（慢、可重跑）。**兩件事分開，因為失敗模式完全不同**：專案建錯要整批 rollback，一個檔傳失敗只該重傳那個檔。

### 3.4 自動建在園展底下：具體要改什麼

1. **`createProjectForProfile` 加 `workspaceId`**：由伺服器以 `findOperatingWorkspaceId(OPERATING_WORKSPACE_SLUG)` 解析，**不接受呼叫端傳入**——照 `uploads/route.ts` 已經做對的形狀。同時 `accessMode` 設 `WORKSPACE_VISIBLE`（否則建完別人看不到）。
2. **先確認 Workspace 的 `name` 到底是「圓展」還是「園展」**（§1.3-H）。`slug` 維持 `yzedtech` 不動（`check-operating-roundtrip.ts:128` 註明服務用固定 slug、不接受注入）。
3. **預設成員與權限**：`WorkspaceMembership` 現有兩個席位（驗證 script 顯示 `yz`、`lily`）。匯入時每個專案的 `ownerId` ＝ Owner 的 profile；`ProjectAccessGrant` 依 `Workspace.defaultProjectAccessRole`（預設 `VIEWER`）給 `lily`。`priorityTier`／封存專案不另給權限。
4. **refCode / 專案編號規則**。現行原型是 `PRJ-2026-004` 流水號，**和使用者的 `00.`–`12.` 對不上**。建議：

```
PRJ-{YYYY}-{SEQ:3}        ← 系統唯一鍵，伺服器指派一次，永不重生成（RES-018）
legacyFolderNo = "01"     ← 使用者的資料夾序號，另存，不唯一（09 被回收過）
displayCode    = "01 共好玟化網站"  ← 列表與 @ 選單顯示用
```
**不要用 `00.`–`12.` 當主鍵**：它會被回收（§1.3-E），而且使用者會繼續在本機新增 `13.`、`14.`，兩邊各發號一定撞。但 **`@` 搜尋必須搜得到 `01`**，因為 Owner 週會上就是用這個號在講話（§1.4 證據）。

5. **`@`-mention 可被索引所需的欄位**。`mentionHits()`（`runtime.js`）對 project 推的是：
```js
DB.projects.forEach(p => push('project', p.id, p.t, `${p.id} · ${p.status}`, 'project'));
```
所以每個專案至少要有 `id`（＝workbenchRef，如 `PRJ-2026-013`）、`t`（名稱）、`status`（顯示字串）。比對字串是 `nm + rid + ds`，**把 `legacyFolderNo` 併進 `ds` 就能讓打 `@01` 命中**。另外 `Occasion` / `OperatingContract` / `OperatingAsset` 都有 `workbenchRef` 欄位，是原型層與 DB 的橋；匯入時必須寫，否則 DB 有資料但工作台 `@` 不到。

#### 階段 5 — 持續同步（之後新增的檔案怎麼進系統）

**建議：不做雙向自動同步。** 理由有三，都不是潔癖：
1. 雙向同步要處理衝突（本機改名 vs 系統改名、兩邊同時改內容），而這批資料**沒有版本控制**，衝突解不了只能二選一，一定會掉東西。
2. R2 key 是 opaque uuid，本機是路徑。雙向同步需要維護一張永久的雙向對照表，而本機檔案可以被任意 Finder 操作（搬移、改名、刪除）且不留痕跡——對照表會悄悄失效。
3. 真正的需求不是「兩邊一樣」，是「**以後新檔只有一個家**」。

**取代方案（三條路，都在系統裡）**：
- **主路徑**：新檔直接上傳到專案雲端硬碟的收件匣（桌機拖放、手機拍照／相簿、`#` 召喚附件——四道門提案已設計）。
- **過渡期單向補傳**：階段 3 的 script 可重跑（幂等鍵），Owner 在過渡的一兩個月內如果還是習慣存本機，每週跑一次 `--since <date>` 把新檔補進來。**只有本機→系統，沒有反向。**
- **收斂**：過渡期結束後，把 `0_工作區` 改名成 `0_工作區_已遷移_20261015`（**不要刪**），作為只讀的歷史備份。對帳報告 ＋ 這份備份是兩道保險。

| 驗證 | Owner 要動手 |
|---|---|
| 連續 4 週每週檢查：系統檔案數 − 上週檔案數 ＝ 本機新增數（過渡期為 0 代表 Owner 已經改用系統了） | 改習慣。這是整個計劃唯一無法用程式解決的部分 |

### 4.4 整體風險與停止條件

| 風險 | 說明 | 應對 |
|---|---|---|
| **R2 儲存與 Class A 操作要錢** | 出口免費，但儲存與寫入要錢。417 MiB 微不足道，但錄音與影片會跳階 | 提案已建議上線後看一個月帳單再定上限。此次搬遷量級不必擔心 |
| **孤兒 object** | 預簽出去但沒 finalize 的 key，日後算不出屬於誰 | 孤兒清理排程必須和匯入同時上線（提案已列為 P0 的一部分） |
